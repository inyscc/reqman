## Context

动机见 `proposal.md` - Why。以下是塑造方案的现实约束。

**树的现状。** `WorkspaceTree` 的折叠态是组件内视图态 `collapsed: Set<string>`，行的展开判定为 `expanded = view.searching || !view.collapsed.has(id)`，子节点以 `{expanded && children}` 条件渲染。`EntryRow` 的行容器当前 `onClick` 只调用 `actions.onToggle(id)`，并用 `event.detail === 2` 忽略双击的第二击；「选中」不是树自己的态——`App` 从激活标签派生 `selectedEntity` / `selectedRequestId`，`selectEntity` 直接就是 `openEntity`。「树的选中 ≡ 会话标签栏的激活项」是既有硬约束。

**排序与移动的后端已经齐了，只是从未被前端调用过：** `collection_reorder`、`children_reorder`、`folder_move`、`request_move`。其中 `folder_move` 有自环 / 后代 / 跨集合三重校验，`request_move` 把条目追加到目标父级末尾（`MAX(sort_order) + 1`）。渲染侧 `collection_tree` 把文件夹与请求**混排在一个共享的 `sort_order` 空间**里（同序号时文件夹在前）。

**变量现状。** `variables` 表带有 `UNIQUE(scope, owner_id, name)`，因此「同名共存」在存储层不成立；`upsert_variable` 以 (scope, owner_id, name) 定位。`list_variables` 是 `ORDER BY name`；解析层 `layer_for` 在列表上顺序覆写一个 `BTreeMap`，所以"谁赢"取决于列表顺序。导入侧遇到禁用变量会**跳过并记录**（`parse_variables`），导出侧硬编码 `enabled: true`。`VariableDoc` 没有 `description` 字段。

**集合变量的底层能力早已存在：** `Scope::Collection`、`load_scope_layers` 的 collection 层、`pm.collectionVariables`、集合导入导出、`VariablesPeek` 的只读展示——缺的只是编辑入口。`VariablesPanel` 目前把作用域写死为 `environmentId ? 'environment' : 'global'`。

## Goals / Non-Goals

**Goals:**

- 集合与文件夹行恢复「单击即打开」的 Postman 模型，同时不丢失单击展开/折叠的能力。
- 三类行（集合 / 目录 / 环境）的右键入口与「⋯」完全同源：同一份菜单、同一个展开状态、同样不改变选中。
- 集合树支持拖拽排序与同集合内的移动，且能把「目录与请求交错」这个顺序真正落库。
- 变量模型与 Postman 对齐：键可改、变量可禁用、带描述、可拖拽排序、同名可共存并显式标出被遮蔽的行。
- 集合变量获得编辑入口，且不引入第二种变量表格实现。
- 导入导出对禁用状态与描述做到往返保真。

**Non-Goals:**

- 不做跨集合拖动（存储层现有校验明确拒绝；跨集合移动会牵出集合级脚本、变量与认证继承的语义重构）。
- 不为文件夹引入变量作用域——文件夹面板保持只有脚本。
- 不把「初始值 / 当前值」拆成两列呈现（模型里两者都在，编辑器仍写同一个值，与既有行为一致）。
- 不引入变量表格内的搜索或过滤。
- 不做树的多选与批量拖拽。

## Decisions

**D1. 单击目录行 = 打开实体面板 + 切换展开。**

`EntryRow` 的 `onClick` 在现有 `actions.onToggle(id)` 之后追加 `actions.onSelectEntity(entity)`；`onSelectEntity` 已经是「打开或聚焦该实体的标签」，因此重复单击同一行只会聚焦标签，不会新增。保留 `event.detail === 2` 忽略第二击，双击仍只切换一次展开。

键盘 Enter 与单击同义：目录行聚焦时 Enter = 切换展开 + 打开面板（与请求行的 Enter = 打开保持同一语义）。

- 替代方案（否）：`rework-tree-expansion-gestures` 的「单击 = 纯视图动作」——它让「选中 ≡ 激活标签」这条约束继续成立，但也让集合/文件夹面板只剩菜单一条路，并与更早的「选中集合/文件夹在主区打开实体脚本面板」需求互相矛盾。本次取 Postman 模型，代价是浏览树时会累积标签；该代价由「同一实体至多一个标签 + 标签可关闭」承担。
- 替代方案（否）：双击 = 打开。双击的第一击已经切换了展开，第二击再打开会留下「展开 → 回折」的闪烁，要消除闪烁只能给展开回去抖。

**D2. 右键入口从「只对请求节点」扩展为集合 / 目录 / 环境通用。**

三处的实现方式与请求行完全一致：`onContextMenu` 里 `preventDefault()` + 把菜单状态设为该行 id，菜单项直接复用各行既有的 `menu` 数组，锚点仍由 `.node-menu` 的 `top: 100%; right` 决定（不跟随鼠标坐标）。打开菜单**不改变选中**（既有要求），也不改变主区内容。

- 替代方案（否）：按鼠标坐标定位菜单——三处都要新写定位逻辑，且与「⋯」的表现不再一致，正是本次要消除的那种不一致。

**D3. `children_reorder` 改为「一个有序列表」。**

新签名：`children_reorder(collection_id, parent_folder_id, items: [{ id, kind }])`。每项的 `sort_order` 取其在列表中的下标，在一个事务里逐项校验「该 id 确实以该种类挂在这个父级下」后再写入。

理由是现有签名的两类索引空间独立（folders 从 0 编号、requests 从 0 编号），而 `collection_tree` 按共享 `sort_order` 混排——现有签名**无法表达** `R, F, R` 这样的交错顺序。该命令前端从未调用过，改签名的影响面仅限 Rust 侧与测试。

- 替代方案（否）：保留现有签名、只允许同种类排序（目录永远在请求之上）——与渲染侧的混排能力自相矛盾，也不是 Postman 的行为。
- 替代方案（否）：新增一个命令保留旧命令——留一个无人调用且语义残缺的命令，不如直接替换。

**D4. 拖拽的落点模型。**

```
   [目录/集合行]
        |
   +----+----+        落点一：行的上/下半区 -> 插入线 -> 同级排序
   |         |
  行上半区   行下半区
        |
   +----+----+        落点二：行中区 -> 整行高亮 -> 移动进该目录/集合根
```

- 允许的拖动源：请求、目录。集合本身只支持在集合之间排序（`collection_reorder`），不能拖进别的集合。
- 移动落到既有命令：请求 → `request_move`、目录 → `folder_move`；同级重排落到新的 `children_reorder`。
- 悬停在已折叠的目录上短暂延时后自动展开，否则拖进折叠目录只能靠落点高亮判断。
- 搜索态**禁用拖拽**：过滤后的树是残缺的，插入线的「同级」语义会指向一棵用户看不见的列表；与折叠控件在搜索态被禁用同一处理。
- 落点**乐观提交**（先按新顺序重排，再落库），失败回滚并提示；本地 SQLite 写失败罕见，但纪律与既有乐观写入一致。
- 拖拽 SHALL NOT 改变选中、SHALL NOT 关闭或切换已打开的标签（沿用折叠的既有纪律）。
- 跨集合不产生落点（而不是"放下才报错"）：越界拖动直接不显示插入线。

**D5. `window-chrome` 的拖拽边界措辞收窄。**

「拖拽能力 SHALL 仅由会话标签行承载，侧栏与主区其余部分 SHALL NOT 提供拖拽能力」这句写的是**窗口拖拽**（该需求整条都在讲移动窗口与双击最大化），但字面上会否定侧栏内的条目拖拽。改为把限定词写进句子：窗口拖拽能力仅由会话标签行承载。功能上本就互不干扰（树在侧栏，不在会话标签行内）。

**D6. `variables` 表重建式迁移。**

SQLite 无法直接删除表级 `UNIQUE` 约束，只能重建表。新结构在保留全部既有列的前提下新增三列：

```sql
CREATE TABLE variables_new (
    id                TEXT PRIMARY KEY,
    scope             TEXT NOT NULL,
    owner_id          TEXT NOT NULL,
    name              TEXT NOT NULL,
    description       TEXT,
    initial_value     TEXT,
    current_value     TEXT,
    is_secret         INTEGER NOT NULL DEFAULT 0,
    enabled           INTEGER NOT NULL DEFAULT 1,
    initial_readable  INTEGER NOT NULL DEFAULT 1,
    current_readable  INTEGER NOT NULL DEFAULT 1,
    sort_order        INTEGER NOT NULL DEFAULT 0,
    created_at        TEXT NOT NULL,
    updated_at        TEXT NOT NULL
);
```

拷贝时的回填规则：`enabled = 1`、`description = NULL`、`sort_order` 按 `(scope, owner_id, name, id)` 的顺序用相关子查询计数得出（不依赖窗口函数，保证确定性），随后删除旧表、改名、重建 `idx_variables_owner`。

- 旧库不可能存在同名重复（唯一约束），因此「启用 + 无描述 + 按名称排序」正是今天的行为，迁移后表现不变。
- 替代方案（否）：只加列、保留唯一约束，把重复键仅做成界面态——那样「上面一条覆盖下面一条」就没有可持久化的载体，关掉面板就丢，等于没有这个功能。

**D7. 重复键模型与生效/遮蔽判定。**

- **生效**：同一 `(scope, owner_id, name)` 组里**最靠下的启用行**的值生效。
- **回退**：生效条被禁用时，**退回该组里上一条启用行**；全组禁用 → 该名字整体视作未定义（引用处保留占位符，发送前按既有「未解析变量」拦截）。
- **不可读的 secret** 的值不参与解析（既有行为），因此它会自然退到上一条可用行。
- **遮蔽标记**：判据是「该行启用，且同名组里存在更靠下的启用行」——被禁用行、以及当前生效行都不标记。标记纯由前端从列表推出。
- **掩码边界**：`secret_names` 必须跟随生效行改写（生效行非 secret 时要把该名字从集合里移除），否则会出现"掩码按上一条 secret 行的身份施加"的错误。

后台实现上这正是既有 `layer_for` 的语义：在列表上顺序覆写、跳过禁用行，天然得到"最后一个启用的赢、全禁用即未定义"。前提是 `list_variables` 确定为 `ORDER BY sort_order, name`（现在是 `ORDER BY name`）。

**D8. 顺序即用户意图。**

`sort_order` 的分配规则：新增（幽灵行提交、脚本 `set` 新键、导入）一律**追加到末尾**（`MAX(sort_order) + 1`）；**改名不移动位置**；拖拽后整组重编号（`variable_reorder`）。列表顺序完全由用户与追加语义决定，不再按名称字母序——这正是「谁覆盖谁」可被用户直接操纵的前提。

代价要说清楚：把上面的一行改成已存在的名字时，**它仍在上方，因此它自己被标记为被覆盖**；用户觉得不对就把它拖到下方。

**D9. 编辑器按 id 写入，脚本按名 upsert。**

两条路径必须分开，否则脚本会凭空造出重复行或改错行：

| 路径 | 语义 |
|---|---|
| 编辑器（幽灵行/改名/值/描述/启用/排序/删除） | 按 **id**：`variable_create`、`variable_update(id, patch)`、`variable_reorder`、既有 `variable_delete(id)` |
| 脚本 `pm.*` | 按**名** upsert：更新同名组里生效的那条，没有则追加末尾；`unset` 删除生效条 |
| 导入 | 保持既有 `insert_variable`（原子事务内逐条插入），因此源文档里的重复键会被原样保留 |

`variable_update` 的 patch 字段缺省即「不变」；`value` 同时写入初始值与当前值（与既有编辑器一致）；`name` 允许与既有变量重名但拒绝空名。切换 `is_secret` 需要重编码值，而重编码需要明文——**不可读的 secret 无法切换 secret 标记**，此时报错并保持原状，SHALL NOT 静默降级。描述用空字符串表达「清空」。

三个新命令必须同步注册（`lib.rs`）并进入 `security_audit.rs` 的审计白名单——这是既有规格的硬要求。

**D10. 变量行的形状。**

```
[☐] key            | 值（输入框 / 掩码）  | [✎] [🔒 Secure] [揭示] [删除]  ⚠
    描述（有描述时占第二行，小字）
    ^ 点 ✎ 时在同一位置展开描述输入框
```

- 启用勾选框 = `enabled`，参与解析语义（见 D7）。
- 描述常显在键名下方（有描述时），`.node` 的悬停显示纪律不适用于它——描述是内容而不是操作。
- `揭示` / `删除` 保留在行尾：掩码边界仍是既有规格，Postman 没有揭示入口是因为它不掩码。
- 值的提交语义（回车/失焦提交、Esc 还原、无变化不发请求、未揭示 secret 留空即不修改）全部沿用既有契约，只有「名称列只读」这一条被本次变更推翻。

**D11. 集合面板的两个页签。**

`EntityScriptPanel` 增加 `tab` / `onTab`（`variables` | `scripts`，默认 `variables`），并只在 `kind === 'collection'` 时渲染页签栏——文件夹没有变量作用域，给它一个页签栏只会制造一个空面。页签状态存在会话标签里（`EntitySessionTab.innerTab`），与请求标签的 `RequestSessionTab.innerTab` 同一套做法，因此切走标签不会丢当前页签。

`VariablesPanel` 的作用域改由外部显式给出（`scope` + `ownerId`），环境编辑器与集合面板共用同一个组件；集合变量由 `App` 持有并加载（切换到集合实体标签时取一次，写入后重取），与 `VariablesPeek` 的按需读取互不依赖。

**D12. 导入导出的翻转。**

- `VariableDoc` 补 `description` 字段（与 `HeaderDoc` 同款 `DescriptionField`，可读字符串或 `{content}` 对象）。
- `parse_variables` 不再跳过禁用变量，改为把 `enabled` 带进中间表示；缺少名称的变量仍跳过并记录（那才是真正的不可映射内容）。
- `ParsedVariable` 增加 `enabled` 与 `description`；导入写库时一并落盘。
- 导出在禁用时写 `enabled: false`（与环境文档的既有写法一致；读取侧本来就容忍 `disabled` 与 `enabled` 两种写法），描述非空时写 `description`。
- 结果是「禁用变量被跳过并记录」这条降级处置消失，往返保真度提升，且导入报告不再因禁用变量而产生条目。

**D13. 两个按名读写的前端调用方必须与解析规则同源。**

「最靠下的启用行生效」这条规则落在 Rust 的解析层，但前端有两处自己按「名称 → 值」重建了同一份作用域视图，它们必须遵守同一规则，否则会出现「界面显示的值」与「实际发送用的值」不一致：

- `src/lib/scriptRuntime.ts`：喂给沙箱的作用域本身就是 `{ 名称: 值 }` 映射（沙箱协议按名取值），因此必须**跳过禁用行**、并让同名组里最靠下的启用行胜出；写回时它用「按名找第一条」定位行，而脚本读到的是「生效条」——重复键下这不是同一行，于是 `pm.environment.set` 会更新被遮蔽的那行，甚至因为「值看起来没变」而静默跳过写入。
- `src/components/VariablesPeek.tsx`：同样按名折叠成一份映射，必须跳过禁用行并只把生效条的值当作生效值（呈现规则见 D14）。

替代方案（否）：这套判定在三处各写一遍——那正是本变更要消除的分叉。实际做法是把「同名组里谁生效」抽成一个共用的小函数，由变量表格的遮蔽标记、只读浮层与脚本运行时共同使用。

**D14. 只读浮层列出全部条目，但分别标出被禁用与被遮蔽。**

浮层是只读旁路视图，用户打开它是为了确认「这个名字现在到底解析成什么」。因此它 SHALL 列出该作用域的全部条目（含同名与禁用），并对「被禁用」与「被遮蔽」两种状态分别标注，而 SHALL NOT 把它们的值呈现为生效值。标注判据与变量表格的 ⚠ 同源，避免同一个概念在界面上有两种解释。

- 替代方案（否）：浮层只列生效条目——用户看不到「我禁用的那条还在」，也无法解释为什么某个名字解析不出来。
- 替代方案（否）：全部照列且不加任何标注——那正是今天的行为，会把被禁用的值当成当前值展示，与解析结果矛盾。

## Risks / Trade-offs

- [Risk] 表重建迁移不可逆，出错会丢变量数据。 → 沿用既有迁移机制：失败时版本不推进、原数据可读、保留备份副本；迁移步骤本身只有建表 / 拷贝 / 删表 / 改名四步，且拷贝用相关子查询给出确定性顺序，可用既有内存库测试覆盖「迁移后旧变量仍可读、顺序确定、全部启用」。
- [Risk] 拖拽与既有手势打架：按下后没移动必须是单击（打开 + 展开），移动后才进入拖拽；右键与行内「⋯」也不能被拖拽吞掉。 → 用 HTML5 DnD（`dragstart` 之后不会再有 `click`），并在浏览器用例里同时锁住「按下未移动 = 打开」与「拖拽结束后选中与已开标签不变」。
- [Risk] 重复键让「某个名字解析成什么」依赖顺序，用户可能看不出为什么值不对。 → 把遮蔽显式化（⚠ + 中文提示）并把解析规则同时写进 `variable-engine` 规格与 Rust 单测；勾选框造成的回退也由同一条规则覆盖，不留第二套解释。
- [Risk] secret 标记切换在不可读时无法完成。 → 明确失败并提示，保持原状；不静默降级成明文（那会破坏既有的明文不落盘要求）。
- [Risk] 一次变更横跨五个能力面与一次迁移，评审面大。 → tasks 按五个工作块切分（树手势 / 变量存储 / 变量界面 / 互转 / 测试），每块内保持可独立验证。
- [Trade-off] 单击目录行会累积标签。 → 同一实体至多一个标签，且标签可关闭；这是选取 Postman 模型的既定代价。
- [Trade-off] 跨集合拖动不做，Postman 用户可能会尝试。 → 越界不显示落点，行为上「拖不过去」而不是「放下报错」。
- [Risk] 「同名组里谁生效」这条判定将有三处消费者（Rust 解析层、脚本运行时、只读浮层）与一处呈现（变量表格的遮蔽标记）。四处各写一遍必然漂移，出现「界面说 A 生效、实际发出的是 B」。 → 抽成一个共用判定函数，并在 tasks 里为三处各写一条验证。
- [Risk] 脚本写回定位错行不会报错，且两行值相同时会静默跳过写入——属于静默错误，最难被发现。 → 写回改为按生效条定位，并用单测覆盖「两条同名时写入落在生效的那一条」。
- [Trade-off] 只读浮层在出现同名条目时会把同一个名字列成多行，列表比过去长。 → 刻意如此：浮层回答的是「这个名字解析成什么」，藏掉被遮蔽的行会让标注无处安放。

## Migration Plan

1. 在 `MIGRATIONS` 版本链尾部新增一步（`migrate_variables_to_duplicate_keys`），内容见 D6 的 SQL。
2. 部署即生效：应用启动时按既有机制自动迁移；迁移失败则版本不推进、原数据可读、保留备份副本。
3. 回退：结构变更本身不可逆。需要回退时从迁移前的备份副本恢复（备份能力由 `storage-foundation` 的「备份与恢复」提供）。
4. 旧数据在迁移后表现不变（全部启用、无描述、按名称排序）；前端不需要为旧数据写兼容分支，因为缺省值就是旧行为。
