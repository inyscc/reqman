## Context

动机与范围见 `proposal.md`。实现层面需要理解三处现状：

- **curl 生成**在 Rust：`src-tauri/src/interchange/curl.rs` 用 `parts.join(" \\\n  ")` 装配命令，数据体写死 `--data-raw`（`:83`、`:92`），正文原样引用。请求编辑器（`CurlSnapshot.tsx` 的 `useCurlSnapshot` → `commands.curlExport`）与「导入 / 导出」模态（`ImportExportPanel.tsx:140` → `commands.curlExport`）**共用同一个后端命令**，spec 也因此要求两处口径一致。
- **发送态**是 App 级单例：`sending: { key, attemptId } | null`、`busy: boolean`、`cancelAttemptRef`、`attemptCancelledRef`（`App.tsx:380-388`、`:1419-1436`）；渲染处已按 `sending.key === activeTabKey` 圈定，但 `busy` 全局置位会波及所有标签（发送按钮禁用、底栏「发送中…」、`saveCurrentSurface` 早退）。
- **后端与沙箱已按会话隔离**：`net/cancel.rs` 的 `SendRegistry` 以 `attempt_id` 分组，`cancel_send(attempt_id)` 精确撤销；脚本阶段每段 `createContext()` 新建（`scriptRuntime.ts:1280`，定义 `:215-223`）。并发无需改后端。

## Goals / Non-Goals

**Goals:**

- curl 命令更通用（`-d`）、可按需压成单行、内嵌正文可按需压缩，且与 body 的 `Minify` 同一算法。
- 发送态与取消精确到「发起它的那条请求」；多条请求可同时在飞。
- 底栏忙碌文案不再把保存/改名误报成发送。

**Non-Goals:**

- 改动 curl 快照的编辑控件（仍为纯 `<textarea>`）。
- 改动后端发送/脚本沙箱的并发模型（已就绪）。
- 为并发引入条数上限或队列。

## Decisions

### D1：压缩在后端解析，保持两个 curl 入口同一口径

压缩生效值由**后端**在生成命令时解析：请求级三态取自传入的 `SavedRequest`（`settings` 字段，未保存时来自 `inline`），应用级缺省取自 settings 表。理由：`curl_export` 是请求编辑器与导入/导出模态**唯一的共同生成点**，spec 要求两处内容一致；若放到前端，两处入口要各自解析，迟早分叉。

替代方案：前端解析后传一个 curl 专用布尔给后端——会往共享的 `SendRequestInput` 里塞一个只对 curl 有意义的字段，且两个入口仍需各自解析。否决。

### D2：`-d` 与 `@` 回退由后端逐参数判定

新增一个内部 helper 产出数据体参数：取值以 `@` 开头时返回 `--data-raw`，否则返回 `-d`。判定逐个数据体做，覆盖 raw 与 `x-www-form-urlencoded` 两处；`-F` 与二进制体不经过它。依据是既有的「命令 SHALL 可直接执行」：`-d '@...'` 会被 curl 当文件名读。

替代方案：一律 `-d`（会破坏「可直接执行」）；一律 `--data-raw`（正是要改掉的现状）。均否决。

### D3：后端返回参数序列，前端按生效布局拼接

`CurlCommand` 增加 `parts: Vec<String>`（逐段已 shell-quote），`command` 保留为多行拼接结果。布局是**配置**（应用级缺省 + 请求级三态，见 D10），生效值在前端解析后对 `parts` 用两种分隔符 join——多行 `" \\\n  "`、单行 `" "`——因此两种布局**天然共享同一份参数**，不会出现取值漂移。

请求编辑器的 cURL 标签与导入 / 导出模态都按**同一份生效布局**呈现（模态也从 `parts` 拼接），这样 spec 里「两处内容一致」仍然成立。

**命令旁不放布局开关**：布局是配置，放一个一次性开关在命令旁边，用户改过一次、下次进来又回到配置值，反而难以察觉自己改的是「这一次」还是「以后都这样」。替代方案（后端接收 `layout` 参数、切换即重新生成）会覆盖用户编辑且与「重新生成」语义重叠，否决。

### D4：两个 cURL 设置的两层取值都落在请求设置与全局设置

请求级三态新增到请求的 `settings`：`curl_body_compress: inherit | compress | raw` 与 `curl_line_layout: inherit | single | multi`（缺省都是 `inherit`），随请求保存；应用级两项缺省各新增一个 settings 键。控制点只有两处——设置模态（应用级）与请求编辑器的 Settings 标签页（请求级）——与「折行」三态完全同构。

**命令旁不加速捷开关**：布局与压缩都不再出现在 cURL 动作行（见 D3）。一次性开关与「持久配置」混在同一行，会让「这次生效」与「以后都这样」变得难分。

### D10：压缩按内容判定，不按语言选择

内嵌正文是否可压缩，取决于**正文本身**：尝试作为 JSON 紧凑化，成功即采用紧凑形式，失败即原样。不再看 `raw_language`。

原先按 `ResolvedBody::Raw.content_type == "application/json"` 判定，会漏掉一类常见输入：请求体语言未设置（`raw_language = null`）时前端按 json 呈现、后端按 text 处理（`variables/mod.rs` 的 `unwrap_or(Text)`），于是「看着像 JSON 的正文」不发 `application/json`、也不压缩。按内容判定与语言选择解耦，这类输入自然被覆盖。

紧凑化实现见下一条：保键序 + 失败即原样。

### D11：紧凑化在 Rust 用「校验 + 剥空白」，不用 serde_json 重序列化

`serde_json` 的默认对象是排序映射：`parse + to_string` 会把 `{"b":1,"a":2}` 变成 `{"a":2,"b":1}`——压缩不该重排用户的键序（硬约束）。因此：先用 `serde_json` **校验**合法性，再在**字符串之外**剥掉结构性空白。键序、数字字面量、转义一律保持原样。

代价是两处**语义等价**的边角差异（相对 JS 的 `JSON.stringify`）：重复键不被合并、显式转义（`\uXXXX`、`\/`）不被归一。因此 spec 把「复用同一实现」表述为「同一压缩语义 + SHALL NOT 重排键序」，而不是字面上的同一个函数。

替代方案：给 `serde_json` 开 `preserve_order` 再重序列化——仍是重序列化，数字字面量（`1.0`）与转义仍会与 JS 不一致，且要改一个全局特性的行为。否决。

### D5：发送态改为按标签的容器，取消出口随会话

`sending` 由单槽改为按 tab key 的映射，每项持有自己的 `attemptId` 与取消出口；`openAttempt()` 不再写共享 ref，改为返回一个自带取消回调与标志的会话对象。渲染层现有的 `sending.key === activeTabKey` 判定沿用。

替代方案：仍保留单槽、只把 UI 禁用按标签化——无法满足「同时发送两条」，且取消会退化成「取消最后一次」。否决。

### D6：`busy` 与发送解耦

`performSend` 不再置 `busy`；`busy` 只由保存请求、保存脚本、改名置位。底栏的「发送中」改为由「发送态容器非空」派生。这样既支持并发，也顺带修掉「保存中误报发送中」。

### D7：错误与脚本门禁归到发起它的那条发送

发送相关的错误提示（请求失败、脚本错误）与脚本门禁都按发起它的 tab key 承载并呈现，避免并发时两条发送的错误互相串台。门禁并发场景罕见，但同属这条耦合，一并收敛。

### D8：关闭在发标签即撤销该次发送

关闭标签时若该标签有在飞的会话，调用其取消出口并向后端 `cancel_send(attempt_id)`；结果丢弃。避免出现「界面已没有该请求、后台仍在跑并写库」的悬挂。

### D9：并发写同名变量 = 后完成者胜（已知差异）

两条并发发送各自在脚本开始前读一份变量快照、结束时写回，因此对同名变量的写入是 last-writer-wins。这是并发固有的可观察语义，不是缺陷，记入本档；不在本次引入跨会话的写入合并。

## Risks / Trade-offs

- [curl 快照的正文不再与请求体逐字节一致] → 同一算法（body 的 `Minify`）、语义等价；spec 已把「快照」定义为命令口径而非字节一致，并新增场景锁定「压缩复用 Minify」。
- [并发发送下变量写入 last-writer-wins 可能让人意外] → 记为已知差异（D9）；请求脚本本就少见依赖跨请求顺序。
- [取消必须精确到会话] → 若沿用单槽会退化为「取消最后一次」，spec「请求取消」已新增场景锁定「后开会话不夺走取消能力」。
- [新增设置字段的反序列化兼容] → 请求 `settings` 新字段与应用级新键都必须有缺省回落（旧数据缺失该字段时按 `inherit` / 开启处理），两侧（Rust serde、TS）都要覆盖。
- [不限并发条数] → 极端情况下大量在飞请求；由既有单请求体积上限与超时兜底，本次不引入队列。

## Migration Plan

无数据迁移。新增设置键与请求设置字段一律带缺省，旧数据读取即回落缺省值（压缩生效、布局多行）。回滚只需撤销代码；已写入的额外设置字段/键被旧版本忽略。
