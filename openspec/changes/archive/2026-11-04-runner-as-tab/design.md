# Design

## D1 为什么是标签，不是「再做一个侧栏面板」

运行器的三个问题（跑什么、跑成什么样、怎么跑）需要横向空间，三列是它的基本形态；侧栏或抽屉都容不下。标签页给的是**整块主区**，与请求编辑器同一档面积，因此不需要为它另设一套布局规则。

更关键的是**切换成本**：标签切换是这个应用已有的、用户已经会用的动作。把运行器做成标签，「跑 → 改 → 再跑」就是两次标签切换；做成模态则要先关再开，而关闭会中止本轮。

## D2 常驻挂载，只按激活态显隐

`RunnerPanel` 的收尾挂在**卸载**上（关掉界面不能留下继续发请求的幽灵），这个约束本身是对的，不能为了标签切换而放宽。

于是问题变成「切走时不该卸载」。做法：所有运行器标签都渲染在主区里，非激活的那些用 `hidden` 藏起来——

- 切换标签不触发卸载，运行继续，结果留在组件自己的 state 里；
- 真正关掉标签时才卸载，收尾照旧生效；
- 不需要把 `results` / `outcomes` / `selected` 提升到 App：那会让一个自洽的面板被拆成两半（组件一半、App 一半）。

代价是运行器标签不能太多（每个都留一份完整结果在内存里）。这是可接受的：同名目标本来就只有一个运行器标签（D3），而一次运行的结果本来就是重的东西。

**被否掉的方案**：把运行状态提升到 App 或全局 store。它能做到「卸载也不丢」，但要重写 `RunnerPanel` 的整套状态与运行循环，且让一个纯展示组件开始依赖外部容器——收益不足以抵掉这次改动的风险。

## D3 同一目标至多一个运行器标签

key 是 `runner:<kind>:<id>`。重复点「运行」只聚焦，不开第二个：同一份名单开两份，两份结果互不相干，用户还得自己分辨哪份是新的。

这也意味着**名单在设计上是「打开那一刻」的事实**：想换名单就关掉重开，而不是在同一标签里换一批请求、却留着上一轮的结果。

## D4 打开运行器时，来源标签先转常驻

集合 / 目录标签是**预览标签**（点一下就开，下一次打开会顶替它）。运行器要占一个普通标签位，如果来源标签仍是预览，`insertTab` 会拿运行器的插入行为去填预览槽位——刚点过「运行」的那一页反而被顶掉。

因此打开运行器前先 `pinTab` 来源标签。语义上也说得通：点「运行」是对这一页的明确操作，这一页不该是「一瞥」。

## D5 明细就地呈现，不开新标签

点名单里的一条 = 选中它，右侧明细面板换内容。这与 Postman Runner 的做法一致（那里点请求名才会开新标签，而那个新标签是**请求本身**，不是结果）。

本产品不做那个「点名字开请求标签」的入口：运行器标签已经能切到请求标签，而"看到第 3 条失败 → 去改它"的路径是用户自己按需走的，不该由一个点击热点替他决定。

## D6 运行器标签不持久化

标签集合记的是「开着哪些页」。运行器的内容（名单、门禁结论、每一条的结果）都在内存里，重启后恢复出来的只会是一个空壳——还得重新收集名单、重新问门禁。**不如不恢复**：关掉应用就是这一轮的终点。

激活项若正停在运行器上，持久化为 `null`（恢复时落到第一个标签），避免存下一个恢复时认不出的 key。
