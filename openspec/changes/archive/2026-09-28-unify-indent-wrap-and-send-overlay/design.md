## Context

动机见 `proposal.md`。这里只记影响做法的现状与约束：

- **缩进现在是两个互不相干的值**，各自有独立的持久化键与独立的消费方：`EditorAppearance`（`editor_appearance:indent_count` / `indent_type`）只喂 Monaco 的模型选项（`src/components/CodeSurface.tsx:41-58`）；`ResponsePresentation.indentWidth`（`response_presentation:indent_width`，取值 2/4/8）只喂响应格式化（`src/components/ResponsePanel.tsx:171`）。请求正文的 `Beautify` 两个都不看，硬编码 2 空格（`src/lib/editing.ts:24-27`）。
- **外观改动有一条既有纪律**：改外观只 `updateOptions`，**不重建编辑器**——重建会丢滚动位置与折叠状态（`src/components/CodeSurface.tsx:188-198` 的注释与 spec 场景「外观改动作用于已打开的编辑面且不重置视图」）。折行必须走同一条路。
- **发送态与忙态是分开的**：`busy` 被保存请求、保存实体脚本、改名共用；`sending` 才是发送态（`src/App.tsx:376-381`）。响应头当前的「发送中…」徽章挂在 `busy` 上（`src/components/ResponsePanel.tsx:204`），`ResponsePanel` 目前只收到 `busy`。
- **发送期间旧响应不会被清空**：响应存在每个请求标签里（`src/App.tsx:464`），只在成功后覆盖、失败时清空。所以遮罩有"无内容可盖"与"有内容可盖"两种形态。
- **动效基线**：`2026-09-19-rework-visual-system-and-app-chrome` 的 `design.md` 定下按下/悬停 120ms、浮层入场 180ms，并明确列出"**发送中的状态切换不加动效**"；`App.css` 至今**没有任何 `@keyframes`**，`prefers-reduced-motion` 有三处先例（`App.css:1241/1862/2748`）。
- **色值必须进 token**：`App.css` 的 `:root` 之外不允许出现 hex 字面量（同上归档 change 的任务 1.7）。
- **设置的行式布局与控件形态是规定好的**：名称在左、控件在右；互斥选项用通用下拉，布尔项用开关（`ui-layout`「设置列表的行式布局」）。
- **请求级设置已有一个可照抄的模板**：「响应格式」一行——三态、随请求保存、计入未保存守卫（`src/components/RequestEditor.tsx:1296-1314`）。

## Goals / Non-Goals

**Goals:**

- 缩进在全应用只剩一份取值，它同时驱动编辑面与 JSON / XML 的格式化输出；两个缩进相关字段立刻"有反应"。
- 长行可读：折行为缺省行为，且可在应用级与请求级调整。
- 发送进行中，响应区能明确表达"在等响应"，且不牺牲已有响应的可恢复性。

**Non-Goals:**

- 不改脚本编辑面的折行行为（用户只要请求与响应），也不改 cURL 快照文本域等小输入面的换行——它们本就不是代码编辑面。
- 不做深浅色主题、不做响应区字体独立设置。
- 不新增 npm 依赖，也不新增 Rust 命令；但请求级折行要落到 Rust 的 `RequestSettings` 上，这是数据处理而非命令面改动（见 D8）。
- 不开口径去改底栏状态条的忙态语义（见 D9）。
- 不为格式化输出提供第二处缩进入口（这正是被删掉的东西）。

## Decisions

### D1：缩进合并为唯一真源，取值域由「{2,4,8} 空格」换成「1–8 × {空格,Tab}」

`EditorAppearance` 成为全应用唯一的缩进来源：`indentCount`（1–8）与 `indentType`（space / tab）既写给 Monaco 的模型选项，也传给 `renderBody` / `prettyJson` / `prettyXml` / `formatRawBody`。

关键实现点：**Tab 缩进下"每层一个制表符"，宽度由编辑器的 `tabSize` 呈现**。

- JSON：`JSON.stringify(value, null, '\t')`（第三个参数为字符串时即每层缩进字符串）。
- XML：把 `prettyXml` 里的 `' '.repeat(indent)` 换成等价的缩进单元。
- Monaco 侧 `tabSize = indentCount`，因此同一个制表符在编辑面与格式化输出里显示宽度一致——两处观感自动对齐，这正是合并带来的额外收益。

取值域从 `{2,4,8}` 扩到 `1–8` 的任意整数：**不丢任何既有能力**（2/4/8 仍在域内），并且与 Postman 的 `Indentation count` 同域。

替代方案（保留两处缩进，只给"格式化缩进宽度"补一个 Tab 选项）：改动更小，但"改了编辑器缩进没反应"的困惑原样保留，且与 Postman 的形状不符——否决。

### D2：旧键不迁移、不清理

`response_presentation:indent_width` 从此不再读取。**不做一次性迁移**，理由：

1. 两个设置的语义不可通约——旧键是"我读响应时想看到多宽的缩进"，新值是"这个人在编辑面里的缩进"，把它灌回去会用一个阅读偏好去驱动编辑行为。
2. 迁移会让"缺省 4"这条规定出现例外：用户看到的行为取决于一个他已经忘记的设置。

也不主动删除旧行：一次无意义的写操作只会把坏值风险带进来。存储里留一个不再被读的键是可接受的（既有 `readPresentation` 对读不懂的值本就回落缺省）。

替代方案（仅在新的缩进数键缺失时用旧值播种）：否决，理由同上第 1 条。

### D3：折行的取值是两层三条路，面板开关写的是请求级值

- 应用级缺省：`editor_appearance:wrap` 布尔，**缺省开启**。
- 请求级：`SavedRequest.settings.wrap_lines?: 'inherit' | 'on' | 'off'`，缺省 `inherit`——与既有 `response_format` 完全同款（可选、不迁移、`inherit` 即跟随）。
- 生效值解析：`resolveWrapLines(全局布尔, 请求三态)`，与 `resolveInitialFormat` 同形。
- 两处面板开关（请求 Body 类型行、响应正文工具条最右端）都以两态呈现，点击即把请求级值落为**显式**值（与当前生效值相反）；`inherit` 只在请求 Settings 标签页里可选。三者是同一份取值，改动都计入该请求的未保存守卫。
- **解析规则只有一处陈述**：取值与解析写在 ui-layout「折行」，`code-editors`「代码编辑面的折行」只引用它并规定呈现。同一个规则在两份规格里各写一遍，改一处必然忘另一处。

替代方案 A（只在应用设置里放一个全局开关，不做请求级）：我最初的推荐。否决——与 Postman 的形状不符（它的折行是响应区工具条上的按钮），且会把脚本编辑面一并卷进来。

替代方案 B（面板开关只作"本次查看"的临时覆盖，像格式下拉那样不持久）：否决——用户要求它同时出现在请求设置页，两层显示同一状态才说得通；且临时覆盖会在每次新响应时重置，用户要反复点。

### D4：折行只改呈现，落在编辑器的选项与纯文本面的 CSS 上

- Monaco 侧走 `wordWrap: 'on'`（按视口宽度折行），与字体/缩进同一条 `updateOptions` 通路，**不重建编辑器**。
- 降级面（`.body`，大正文 / 二进制回退）由 `white-space: pre-wrap` 改为按开关在 `pre-wrap` / `pre` 之间切换。Hex 的 `.hex-body` 固定 `pre` 不动——它的理由（三列靠空格对齐）已在 `App.css:2572` 写明。
- 不引入 `wordWrapColumn` / 折行列数设置：没有需求，且会多出一个设置项。

### D5：发送反馈的动效是本仓库第一处循环动画，显式覆盖动效基线的一条边界

**决定**：发送态下正文区覆盖一层半透明的灰白遮罩（把旧响应压暗而不抹掉），正文区**顶边**有一条 2px 进度线，线上一段亮色从左往右循环跑过（跑马灯）；周期 ≥1.2s；`prefers-reduced-motion: reduce` 下撤掉跑动的那一段。

**为什么可以覆盖**：既有基线排除的是"发送中的**状态切换**"——指发送/取消按钮换形态这类**瞬时过渡**，动画只会让高频操作显得慢。遮罩 + 进度线是**进度指示**：它不推迟任何东西，而且在长请求下，没有它用户无法判断请求是否还在进行。因此这条边界改写为"发送中不加入场过渡，但允许以遮罩与进度线表达进度"。

**边界仍然收得住**：零动画下加载态照样说得清（遮罩、进度线本身、响应头的「发送中」标识，后者是 spec 的硬要求）；跑动的那一段单向、周期不短于 1.2s；只在发送态出现，结束即消失。

**遮罩是灰的、半透明的；进度是顶边的一条线**：`--scrim` 是深色半透明（`App.css:43`），压在正文上会把已有的响应糊成一块不可读的灰，不能用。这里要的是"下面那份还在、只是先不细看它"，参照软件的形状正好就是这个：一层灰色半透明遮罩把内容压暗，正文区顶边一条细线、线上一段亮色跑过。

三版实现都被实机推翻过，理由记在这里以免再犯：

1. **摆占位行**：占位条压在旧响应的文字上读成一层删除线，比不遮挡更难看，而且与"下面那份东西还在"自相矛盾。
2. **遮罩取近白**（`--bg` 一类的浅色）：白底压白底等于没压，进度指示（也是白）跟着看不见——一处取色错导致两处失效。
3. **把进度做成铺满整块的扫光带**：形状就不对。参照里的"跑马灯"是正文区顶边的**一条线**，扫光带压的是"这一块内容"，与下面那份被压暗的响应互相干扰。

因此定为：灰白底 + 顶边一条 2px 线 + 线上跑动的一段亮色，浮层里不摆任何内容。新增的三个色值**进 `:root` token**（D 段约束：`:root` 之外不出现 hex 字面量）。

遮罩色**不跟本仓库的冷中性色阶走**：`--bg` / `--border` 那一族是偏蓝的灰（D0 的冷中性），但这一层铺满整块正文区，偏蓝的灰在大面积上被读成"整块变蓝"而不是"被压暗"（实机反馈）。遮罩取中性灰白（R≈G≈B），与参照软件那一块一致。

**触发条件挂 `sending`**：同时把响应头既有的「发送中…」徽章从 `busy` 改挂 `sending`，顺带修掉"保存请求也显示发送中"这个既有瑕疵。

### D6：开关停在正文工具条最右端，显隐由 CSS 驱动

**位置**：开关排在「响应呈现格式」下拉那一行的**最后**（内容类型之后），不覆盖正文。最初按用户指定放在正文区左上角、以浮层呈现；见到实机后改为与参照图一致——Postman 把同类开关放在同一行的右端。这一改动同时消掉两处代价：不再压住正文首行的行号栏，也不再与正文的滚动条抢指针。发送遮罩只铺在正文区（`.response-body-area`），开关在工具条里、处于该层之外，因此天然不会被遮罩盖住——spec 的「工具条保持可见但不可用」由此直接成立。

显隐仍由 `.response-region:hover` 与开关自身的 `:focus-visible` 驱动 `opacity` 与 `pointer-events`：

- 用 CSS 而不是 JS 状态：显隐是纯呈现，走状态会带来额外的重渲染，也容易与 Monaco 的鼠标事件打架。
- `opacity: 0` 而非 `display: none`：开关始终在可访问树上、可被 Tab 聚焦；`:focus-visible` 时同样显形，键盘用户拿得到它。
- 显形前 `pointer-events: none`：避免指针只是扫过就把请求改了状态。
- 显隐只改 `opacity` 与指针事件：位置与占位不变，同行已有的内容类型标签不会因此移位（spec 的「显隐不推动排版」）。

### D7：生效值与写回都收敛在 App 层

`App` 已经解析并向下传 `presentation`；折行照此办理——`App` 解析生效值并下发，同时提供一个"把某请求的折行设为 X"的回调（写请求草稿，天然计入未保存守卫）。`ResponsePanel` 与 `RequestEditor` 都只消费生效值与触发回调，不各自读存储——与既有 `editingRegistry` / `presentation` 的分层一致。

`CodeSurface` 新增一个折行 prop；创建时读当前生效值、订阅回调里 `updateOptions`，与字体/缩进共用同一个 `applyAppearance` 入口。

### D8：请求级折行必须落到 Rust 的 `RequestSettings` 上

**问题**：请求级取值住在请求的 `settings` 里，而该列不是"前端自己说了算"的 JSON——它由 Rust 的 `RequestSettings` 反序列化后再整包写回（`src-tauri/src/storage/requests.rs:62,82`；写回经 `src-tauri/src/storage/proxy_credentials.rs:45` 的 `to_value(settings)`）。前端多出的字段在反序列化时被静默忽略，于是**用户设的请求级折行会在下一次保存后回到「跟随全局」，且没有任何提示**。

**做法**：在 `src-tauri/src/storage/model.rs` 新增一个三态枚举（`inherit` / `on` / `off`，`#[serde(rename_all = "snake_case")]`，`Default = Inherit`）与 `RequestSettings` 上的对应字段，并在 `RequestSettings::default()` 里同步；前端 `src/lib/types.ts` 的可选字段与之对齐。既有的 `ResponseFormatOverride` 就是同一形态的先例（`model.rs:542-561, 665, 677`），旁边还有一条往返测试可照抄（`storage/requests.rs:412-416`）。

**不需要**数据库迁移：`settings` 是 JSON 列；`RequestSettings` 已带 `#[serde(default)]`（`model.rs:651-666`），旧行缺这个字段时照常读入并使用缺省。

**替代方案**（把请求级折行另存一处，例如按 `requestId` 写进某个应用级作用域）：否决。请求级呈现偏好已有既定归宿（`settings`，`response_format` 就在里面），另立一套会多出一个生命周期、清理面与"请求删了但偏好还在"的悬空数据问题。

### D9：底栏状态条的忙态措辞不在本次范围（显式排除）

**事实**：响应的头部徽章与底栏状态条今天都用同一个 `busy` 表示"发送中"（`src/components/ResponsePanel.tsx:204`、`src/components/BottomBar.tsx:29`）。本次只改前者，且**必须**改——遮罩与标识必须由同一个触发条件驱动，否则会出现"遮罩已消失但头部还在说发送中"。

**为什么不顺手改底栏**：`busy` 被保存请求、保存实体脚本、改名共用（`src/App.tsx:376-381` 明说了这件事），把底栏改准需要引入"保存中…"这类新文案与新的状态区分——那是另一个议题，没有需求支撑。

**代价（接受）**：保存请求时，响应头不再说"发送中"、底栏仍在说。这是既有瑕疵的可见化，不是本次引入的缺陷；留作后续议题。

## Risks / Trade-offs

- [响应格式化的缺省缩进由 2 变 4，所有用户可见] → 已在 proposal 标 **BREAKING**；只影响格式化输出的观感，不改变任何文本内容。
- [旧键不迁移会丢掉部分用户显式设过的宽度] → 接受（语义不可通约，见 D2）。若日后有反馈，可在设置界面之外做一次性播种，但不在本次范围。
- [Tab 缩进的正文复制到别处可能不被某些查看器接受] → 只有用户主动选 Tab 才发生；缺省是空格。
- [开关悬停即现、点击即让请求进入未保存态，存在误点] → 显形前 `pointer-events: none`；误点的代价与改动「响应格式」一致（一次守卫询问），可接受。
- [开关只占 24px 图标、且悬停响应区才显形，可能被忽略] → 它与呈现格式下拉同行、位置固定，且悬停响应区即显形；参照图在同一位置有同样的可见度。若日后仍觉隐蔽，改成常显只涉及 `opacity` 一处。
- [折行开启后长 JSON 的"一行一条记录"扫描性下降] → 折行是可控开关；折叠能力不受影响。
- [进度线是本仓库第一个循环动画，牵动无障碍与绘制开销] → reduced-motion 下撤掉跑动的那一段；单向、周期 ≥1.2s；用 `transform` 驱动，避免触发重排；只有 2px 高，绘制面积可以忽略。
- [再次发送时遮罩压住旧响应，用户暂时无法细看它] → 遮罩半透明，旧响应在遮罩下仍可辨认；发送结束即恢复，且失败/取消都不丢旧响应。
- [响应头与底栏的忙态措辞会在"保存请求"时短暂不一致] → 已知并显式排除（D9）；响应头那一处改动是必需的，底栏留作后续议题。
- [请求级折行若漏改 Rust 结构体，会在保存后静默回到「跟随全局」] → 已作为 D8 的独立决定与 `tasks.md` 中的独立任务固定下来，并用往返测试兜住（保存后读回，字段仍在）。
