# Design

## Context

动机见 `proposal.md - Why`。与设计相关的现状：

- 标签集合是 `App.tsx` 里的一个 `SessionTab[]`（`tabs`）+ 一个 `activeTabKey`，**主区显示什么由 `activeTabKey` 唯一决定**；标签的增删改都汇到少数几个入口：`openRequest` / `openEntity`（树单击）、`createRequest`、`duplicateRequestById`、`requestSave` 回写、以及启动时的恢复。
- 「打开」有两个入口函数，已经统一收口（`openRequest` / `openEntity` 里各自有 `if (tabsRef.current.some(...)) 聚焦否则新增`）。预览顶替只需要改这两处 + 三处「显式新增」的入口。
- 标签行是 `.session-bar` 里的一行 flex：`.session-tabs`（唯一可收缩可滚动）+ 环境选择器 + 窗口按钮。`.session-tabs` 的滚动条被显式隐藏（`scrollbar-width: none`），唯一的滚动暗示是滚轮转横向。
- 标签宽度只由内容决定（`flex: 0 1 auto; min-width: auto`），名称的 `min-width: 16px` 允许它一路缩到 16px —— 标签一多，名字先变成省略号残片，再整体溢出。
- 拖拽的既有约定：集合树与环境列表都用 HTML5 DnD，落点用「插入线」，算法在 `lib/treeMoves.ts` / `lib/environmentMoves.ts`，两处同一条规则（先在去掉拖动项的列表里定位目标，再按下标插入；没有变化时返回入参原引用）。

## Goals / Non-Goals

**Goals:**

- 单击树只是「看一眼」：预览槽位至多一个，再打开别的就顶掉它。
- 「留下来的」动作明确且可发现：点标签、改内容、发送。
- 标签多到溢出时，用户知道还有几个、分别是什么、怎么过去；激活的那个永远可见。
- 标签顺序可以拖。

**Non-Goals:**

- 不做「固定标签」（VS Code 里钉在最左侧、不可关闭的那一类）：那是另一层语义，本变更只区分「会被顶替」与「不会」。
- 不做标签最大数量上限、不做标签组、不做「按名称排序」。
- 不动「关闭」的守卫语义：顶替只发生在未被留用（因此一定没有未保存改动）的标签上，见 D3。

## Decisions

**D1 预览槽位是全局的一个，不是每个标签自己的开关。**
「同时至多一个预览标签」是这条规则的**全部**约束：判断只需要 `tabs.find(tab => tab.preview)`，不需要额外记「上一个预览是谁」。顶替时把新标签放在**旧标签原来的下标**上——位置不变，用户不会看到标签莫名跳到末尾。

**D2 「转常驻」的判据是「用户表达过要它留着」，而不是「它被激活过」。**
清单：点击标签本身、在标签里改动内容（草稿变脏）、发送、从树菜单里改名、复制、新建、在树里再次选中同一个请求。**不包括**键盘导航（Ctrl+Tab / Ctrl+1..9）与切内层页签——那些只是「路过」，把路过也当成留用，预览就失去意义（预览的唯一作用就是「路过不留痕」）。

**D3 脏标签绝不被顶替。**
顶替 = 丢弃那个标签的编辑面。虽然按 D2 一旦改动就会转常驻、理论上到不了这一步，但这条判据必须写进顶替逻辑本身：它是**安全边界**，不是「上面已经保证了所以不用检查」。同一个理由，被顶替的标签若还有在飞的发送，走 `cancelOnRemoveRef` 撤销它那一次（与关闭同一套出口）。

**D4 预览标记不持久化。**
存档里不带 `preview`，恢复出的标签一律常驻。反过来做（把预览也存下来）的后果是：重启后第一个单击就会顶掉上次的现场——一次误点换来一次数据消失，代价与收益不成比例。

**D5 标签的可读最小宽度由**名称**的下限给出，不给标签写死 `min-width`。**
写死 `min-width: 96px` 的老问题还在注释里：短名字的标签被撑开、留白落在关闭入口之后，同一行出现两种留白。改成给 `.session-tab-name` 一个可读下限（方法徽标 + 名称下限 + 关闭位 = 标签的自然最小宽度）：短名字照旧贴着内容，长名字到不了「只剩几像素」的残片，超出部分由滚动承接。

**D6 溢出按钮是**覆盖**在标签行两端的浮层，不占布局宽度。**
若把按钮做成占位的 flex 项，就会出现「有按钮 → 标签区变窄 → 溢出；没按钮 → 变宽 → 不溢出」的判定抖动（按钮自己把自己开关掉）。覆盖式没有这个问题：标签区的宽度与「是否显示按钮」无关。代价是按钮会盖住端头的一小段，因此按钮带渐变底、只在对应方向真有溢出时出现。

**D7 激活标签自动滚进可见区，用手算 `scrollLeft` 而不是 `scrollIntoView`。**
`scrollIntoView` 会连带滚动所有祖先（主区、页面），在 `overflow: visible` 的 `.session-bar` 与滚动的主区里表现为「切个标签页面跳一下」。只调整标签容器自己的 `scrollLeft` 就能达到「激活标签可见」的效果，且不影响别处。

**D8 「全部标签」菜单复用既有的浮层约定：portal + `useMenuPlacement`（右缘对齐）+ `useMenuDismiss`。**
菜单里每一行是「跳转按钮 + 关闭按钮」两个**并列**的按钮，不是一个按钮里套一个按钮（后者是非法 HTML，键盘与读屏都会出错）。关闭走既有的 `requestCloseTab`，因此未保存守卫照旧生效。

**D9 拖动排序复用单层列表的既有算法。**
把 `moveEnvironmentId` 的算法抽成通用的 `moveIdInOrder`（环境侧保留原名，调用点不动），标签直接用它。三处拖拽的落点语义因此必然一致：落点的前半 = 插到它之前，后半 = 插到它之后；无变化时不画插入线、也不受理放下。拖动**开始时**把标签转常驻——排位置本身就是「我要它留着」。

## Risks

- **预览语义 x 目录单击**：单击目录行本来就同时「展开 + 打开实体面板」，加上预览之后连续点几个目录只留一个标签。这是有意的（正是诉求 1），但会改变「点过的目录都在标签栏里留着」的旧习惯；反复点同一个目录仍然只聚焦/留用那一个。
- **拖动与窗口拖拽**：会话行同时是标题栏拖拽区，标签是 `button`，已经在 `isInteractiveSessionBarTarget` 的排除清单里；新加的菜单入口与滚动按钮同为 button，不额外处理。HTML5 DnD 在 WebView2 里对 `button` 起拖是可行的（本仓集合树/环境列表已有同款做法），但插入线位置依赖 `getBoundingClientRect`，无布局环境（jsdom）里量不出宽度，因此那一路的用例只能验「重排结果」，几何结论留给浏览器用例。
- **斜体带来的宽度差**：预览转常驻时字重从 400 变 500（`.session-tab.active` 的既有规则），名称宽度会有亚像素级变化，可能让溢出判定翻一次面。D6 的覆盖式按钮保证这最多是按钮闪一下，不会引起重排循环。
- **全部标签菜单在标签很多时的长度**：菜单按 `max-height` 内部滚动（与下拉菜单同一套），不把会话行推高。
