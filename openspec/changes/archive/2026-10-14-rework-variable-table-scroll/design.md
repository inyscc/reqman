# Design

## Context

动机见 `proposal.md - Why`。与设计相关的现状：

- `VariablesPanel` 的根节点是一个普通 `.stack`，里面直接放 `<table class="variable-table">`，自身没有任何滚动容器。
- 两个宿主的高度链完全不同：
  - 集合实体面板：`EntityScriptPanel` 的正文区是 `.pane-body.stack.fill` —— `flex:1; min-height:0` 的**有界弹性列**，但 `overflow: clip`（这是为 Body 的 Monaco 补全浮层准备的，见 `src/App.css` 该处注释）。
  - 环境编辑器：`src/App.tsx` 的 `.pane-body.var-editor` —— 普通块，`overflow: auto`（整页滚），其上是环境名行与代理配置区。
- 项目里已有一套成型的滚动模式：`.table-scroll-wrap`（`position: relative`，定位上下文）→ `.table-scroll`（`flex:1; min-height:0; overflow:auto; scrollbar-width:none` + `::-webkit-scrollbar{width:0}`）→ `<OverlayScrollbar targetRef>`。`KeyValueTable` / `FormDataEditor`、集合树、环境列表都在用它；`OverlayScrollbar` 只读容器几何、不参与布局。

## Goals / Non-Goals

**Goals:**

- 让变量表在两种宿主里都能在自身容器内滚动，且表头吸顶。
- 变量表不绘制任何滚动指示——既不画悬浮细条，也不出现原生占位条（用户明确要求，见 D1）。
- 保持"宿主只提供高度、组件负责滚动"的分工，避免同一张表在两处分叉。

**Non-Goals:**

- 不重构键值表的容器（本变更只复用它的模式）。
- 不改变量表的就地编辑、重复键标记、拖拽排序与幽灵行语义。
- 不为变量表另造第二套滚动条实现。
- 不给变量表画任何滚动指示（含悬浮细条）：这是明确接受的代价，不是遗漏。
- 不给变量表加横向滚动：它是 `table-layout: fixed`、宽度 100%，不存在横向溢出。

## Decisions

### D1 复用键值表的容器，但变量表**不绘制**滚动指示

变量表接进与 `KeyValueTable` 同款的容器：`.table-scroll-wrap` 包 `.table-scroll`（`flex:1; min-height:0; overflow:auto; scrollbar-width:none`），但**不挂 `<OverlayScrollbar>`**——这一处不画任何滚动指示。

理由：容器模式要复用（"宿主只给高度、组件负责滚动"已在四处验证过），但它要解决的两个问题得分开看：

- **原生占位条吃宽度**：由 `scrollbar-width: none`（+ `.table-scroll::-webkit-scrollbar { width: 0 }`）解决。变量表右缘正是一排图标按钮（描述 / secret / 删除、揭示 / 隐藏），占位型滚动条出现时行宽会变、图标会跟着左右跳——这一层必须挡住。
- **要不要画指示条**：不画。用户明确要求这块右缘不出现滚动条；"静止不显形、悬停才出现"的悬浮细条仍然是一条趴在右缘的滚动条（指针停在表格上时它就是常显的），不满足该要求。

代价如实记录：变量表这一处没有滚动暗示，也没有可拖动的指示条，只剩滚轮 / 键盘 / 触控板。这是用户明确选择的取舍，不是实现遗漏。

**规格影响**：`ui-polish`「全局细滚动条」原本把"表格"整体列入强制范围（要求悬浮细条），本变更把它**收窄到键值表**，并为变量表写上例外与例外边界（见本变更的 `specs/ui-polish/spec.md`）。不这样做就会留下两条互相矛盾的规格。

**替代方案（否）**：保留悬浮细条，只把显隐策略改得更克制（例如仅拖动时可见）。指示条若不可见就无从抓起，"仅拖动时可见"等于没有指示条——既没满足用户要求，又白留一个组件与一层定位接线。

**替代方案（否）**：给变量表换成原生细条（thumb 常显）。那正是用户不接受的右缘滚动条。

**替代方案（否）**：保持整页滚动、只把滚动条换成悬浮条。集合那一处的正文区是 `overflow: clip`（为 Monaco 的补全浮层准备的），把它改成可滚会在那条约束上打洞；而且"滚动发生在整页"与"表头吸顶"无法同时成立。

### D2 高度链：宿主提供有界高度，组件只负责容器

- **集合实体面板**：`.pane-body.stack.fill` 已经是 `flex:1; min-height:0` 的有界弹性列，变量表的容器作为它的直接子元素取 `flex:1; min-height:0` 即可吃满剩余高度，`.pane-body.fill` 的 `overflow: clip` 原样不动。
- **环境编辑器**：`.var-editor` 从"普通块 + 整页滚"改为弹性列（`display:flex; flex-direction:column; min-height:0`），标题行与代理配置区 `flex:none` 保持自然高度，变量表容器吃剩余高度。

理由：把"由谁滚"定在组件内部，宿主只提供高度。否则同一张表在两种宿主的滚动行为会再次分叉——环境编辑器那处会退化成"整页滚、表头不吸顶"。

### D3 环境编辑器保留一层兜底滚动，但不用占位型滚动条

环境编辑器里除了表格还有代理配置区，内容高度可变。为避免"窗口很矮时标题 + 代理区把表格压没、或底部内容够不着"，采用两层：

- 变量表容器在环境编辑器里带一个**最小高度**（保证表格至少可见数行），因此表格区不会被压缩到不可用；
- `.var-editor` 保持可滚动（`overflow: auto` + `scrollbar-width: none` + 一个 `OverlayScrollbar`），但它**只在窗口矮到"标题 + 代理区 + 表格最小高度"都放不下时才溢出**。正常高度下外层不溢出，`OverlayScrollbar` 在容器不溢出时不渲染任何东西，因此常规窗口下这块界面看不到任何滚动指示；只有窗口矮到兜底溢出时才出现外侧那一条——它属于编辑面（别名下的代理配置区也要够得着），不在"变量表不画指示"这条例外的范围内。

**替代方案（否）**：`.var-editor` 改 `overflow: clip`。极端高度下底部内容直接够不着，而这一页的代理配置区是必须可达的（PAC 地址、白名单都在里面）。

**替代方案（否）**：给表格容器 `min-height: 0`、不留最小高度。窗口一矮表格就被压成几像素，等于把病从"滚不动"挪到"看不见"。

## Risks / Trade-offs

- [环境编辑器里出现嵌套的两个滚动容器] → 外层只作极端高度的兜底；正常高度下外层不溢出、不渲染指示。验证时点名"窗口高度足够时看不到任何滚动指示"。
- [变量表长列表没有任何滚动暗示，也没有可拖动的指示条] → 用户明确要求；滚动能力仍在（滚轮 / 键盘 / 触控板），只是界面不给提示。这条取舍写进 `ui-polish`「全局细滚动条」的修订，避免日后被当成回归又加回来。
- [把变量表接进容器后行宽变化、贴右缘的图标位置跳动] → 容器的 `scrollbar-width: none`（+ `::-webkit-scrollbar { width: 0 }`）让原生条不占宽，而指示条本身不再绘制；验证时断言"内容溢出前后行宽与贴右缘控件位置不变"。
- [表头吸顶的参照面从正文区下沉到表格容器后失效] → 与键值表共用同一条 CSS（`.table-scroll thead th { top: 0 }`），但变量表有自己的表头结构（含列宽拖拽中线）；验证时在集合变量页与环境编辑器分别断言"滚动到底部时表头仍可见、行不从表头下方穿透"。
- [只改了集合那一处、漏掉环境编辑器] → 规格里那条「两种宿主里的表现一致」的场景就是这条风险的判据；实现时以它为准收尾。

## Migration Plan

无数据迁移：变更只涉及布局与滚动容器，不涉及存储格式，也不改变任何变量的读取含义。
