## Context

`pm.request` 的请求头从上一版起就是"真能力"：脚本改了它，改动会落进实际发出的请求，并按「集合 → 目录链 → 请求」接力。请求体走的是另一条路——喂进沙箱的是**解析后**的文本，回读结果只用于后置阶段读取，不回写。请求头那套机制（`scriptHeaders.ts` 的差异合并 + `App.tsx` 的合并顺序）已经验证过，这次是把同一套机制复制到请求体上，只多两个新问题：空正文与正文形态。

## Goals / Non-Goals

**Goals**

- 前置脚本改写的 `pm.request.body.raw` 落到实际发出的请求上，原本没有正文的请求同样能写。
- 改写在同阶段的后续脚本段与整个后置阶段可见，三级脚本按「集合 → 目录链 → 请求」累积。
- 脚本没碰正文时，发送路径、载荷与解析行为完全不变。
- 正文形态不允许改写时，明确告知而不是静默丢弃。

**Non-Goals**

- 不改 `pm.request.url` / `method` / 认证：它们仍是快照（与 Postman 的差异照旧，不在这次扩）。
- 不支持表单、多段、二进制正文的改写：沙箱没有建模它们的结构，写回去只会把表单压成一段文本。
- 不做"脚本删除正文"的专门语义：把 `raw` 写成空串即可清空，无需额外的删除动作。

## Decisions

### D1 只搬运差异，不拿回读结果整份替换

喂进沙箱的正文是**解析后**的（脚本要读到本次请求实际要发的内容），待发正文仍是原文（`{{var}}` 原样，交给后端解析并走 secret 掩码）。若把回读结果直接当成待发正文，脚本没碰正文的请求也会被写死成解析后的文本——后端那一步解析与掩码等于被绕过。

因此 `diffRequestBody(fed, final)` 只在"回读结果 ≠ 喂进去的那份"时给出改动，`applyScriptBody` 只把这段文本合进草稿。没改动时返回 `null`，调用方完全跳过合并。

### D2 空正文也要喂一个 `body`

没有正文时若沙箱里的请求干脆没有 `body` 字段，`pm.request.body.raw = …` 会撞 `Cannot set properties of undefined`——而"给一个没有正文的请求在脚本里补上正文"正是这个能力的一半用途。`toSandboxRequest` 因此对 `raw` 与 `none` 两种类型**一律**给出 `body: { mode: 'raw', raw: body_text ?? '' }`。空串与"没有正文"在读面上等价，脚本读 `body.raw` 得到 `''` 而不是抛错。

### D3 接力状态独立于请求头，且只在前置阶段接力

`runScriptPhase` 里新增 `currentBody`，与 `currentHeaders` 并排：每段执行完把回读的正文并入，喂给下一段。后置阶段不复用这条接力——后置脚本改的是"已经发出去的请求"，没有回写的落点，读了也只剩一份没人会用的副本。

### D4 改动即走内联发送

`applyScriptBody` 报 `changed` 时，App 必须把 `saved_id` 置空、以 `inline` 发出：后端对 `saved_id` 优先，带着它发过去，内联的那份合并结果会被整份忽略——这正是当初请求头"改了没用"的根因。头与体的改动任一存在都走这条路。

### D5 形态不支持时给一条 warn，不静默

表单 / 多段 / 二进制正文在沙箱里只是文本投影，脚本改了它，`applyScriptBody` 返回 `ignored`。此时 App 往本次 console 里追加一条 `console.warn` 级别的说明（"请求体不是 raw 形态，脚本对请求体的改动未生效"）。理由：静默丢弃会让用户以为脚本没执行；抛错会把一次本来能发的请求拦下来，代价过大。

### D6 补正文时类型随之变为 `raw`

原本 `kind: 'none'` 的请求被脚本写入正文后，草稿的 `kind` 变成 `raw`，语言沿用原值（空则由编辑器按 JSON 呈现）——不在运行时替用户猜一种语法。这一条只影响本次发送的内联副本，不写回库里的请求（脚本改动从不落库）。

## Risks / Trade-offs

- **`url` / `method` 仍改不动，与 Postman 不一致** → 明确写在规格的"其余字段仍是快照"里，并在 `pmDts.ts` 的注释与补全面上只声明 `body.raw` 的写面，不让用户以为改得动 URL。
- **表单正文的改写会被拒** → 有 warn 兜底；要真正支持它，得先让沙箱与解析层交换字段级结构，那是另一个量级的改动。
- **脚本把正文改成与原文相同的文本时不算改动** → 差异比较按文本相等判断，结果相同即不合并、走原路径。代价是无法表达"改了但改成一样"，而那本来也不需要表达。
- **解析后的正文进沙箱、原文进待发请求** → 两处文本可能不同（变量已替换 / 未替换）。这正是 D1 要的：脚本读解析后的，后端收原文的。

## Migration Plan

无数据迁移、无命令变更、无存档兼容问题。回滚需撤掉 `scriptBody.ts`、`scriptRuntime.ts` 的回读与接力、`App.tsx` 的合并顺序与 warn。
