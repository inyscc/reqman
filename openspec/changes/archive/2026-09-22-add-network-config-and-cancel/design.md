## Context

动机与范围见 `proposal.md`；行为契约见 `specs/`。这里只记当前状态与约束中决定做法的那些部分。

- 超时的生效值目前由 `build_client` 直接读 `resolved.settings.timeout_ms`，缺省落在一个常量上。代理则走另一条路：先在 `send_request` 里 resolve 成 `ProxyDecision`，再把决定交给 `build_client`。超时应当采用后者那种形状。
- `RequestSettings` 以 JSON 文本存于 `requests.settings` 列，结构体带 `#[serde(default)]`，加字段不需要 schema 迁移。
- `ProxyConfig` 分布在三处：应用设置表、`environments.proxy` 列、`requests.settings` 里嵌套。它同时是持久化类型与传输类型。
- 代理求解的现状是 `resolve_proxy` 取第一个 `is_effective()` 的层，而 `ProxyMode::None` 被判为不生效——"未配置"与"不使用代理"因此collapse成同一种状态，请求级界面写出的 `proxy = null` 会被跳过并顺位到全局。
- 加密通路的现状：`secrets::encrypt_value / decrypt_value`（AES-256-GCM，`base64(nonce || ciphertext)`），密钥来自 `KeyProvider`，凭据库不可用时拒绝落库。Cookie 与 secret 变量都已走这条通路，代理凭据没有。
- 一次发送在前端是 `variables_preview → 前置脚本 → send_request → 后置脚本`；前置/后置脚本跑在前端沙箱里，`executeOne` 的 Promise 唯一的兑现点是沙箱回调；脚本内的 `pm.sendRequest` 经桥回宿主，宿主再调 `commands.sendRequest`。
- `performSend` 里一个 `busy` 同时代表发送、保存请求、保存实体脚本与改名；`send_request` 的失败分支会无条件清空响应区。

## Goals / Non-Goals

**Goals:**

- 超时成为可配置的两层结构（应用级缺省 + 请求级覆盖），三态无歧义。
- 三级代理全部可配，且每一层都能表达"直连"而不被更低层级接管。
- 代理凭据进入既有的加密通路，落库与回传都不出现明文。
- 一次发送全程可取消，覆盖脚本段与脚本内发起的请求；取消不呈现为失败，且不留下未收尾的资源。
- 三项配置落在与 Postman 同构的位置上，形态沿用仓库既有的行式设置列表。

**Non-Goals:**

- 不做环境级超时（超时保持两级；代理保持三级，二者层级数不一致是有意的）。
- 不放开并发发送；"同时只允许一次发送"这条现状不改。
- 不新增取消之外的发送控制（暂停、重试、排队）。
- 不把代理凭据搬到独立存储表；不引入第二套加密实现。

## Decisions

### D1 超时的生效值在 send 路径解析成 `Option<Duration>`，由调用方交给 `build_client`

`build_client` 保持纯函数：它接收已 resolve 好的代理决定，也同样接收已 resolve 好的超时。解析函数放在 `limits` 里，形状照代理：

```
effective_timeout(db, settings) -> Option<Duration>
     Inherit   -> 读应用级设置（缺省 30_000）
     Unlimited -> None          // 不调用 .timeout()
     Custom(n) -> Some(n)
```

- 备选：让 `build_client` 自己读库。被否——它现在不持有 `db`，加进去会把存储依赖塞进一个本该是纯组装的地方，且与代理的既有形状不一致。
- 备选：在 `resolve_request` 里把生效值填回 `resolved.settings`。被否——变量解析器不该依赖应用设置，且解析预览也会被卷进同一语义。
- `limits::DEFAULT_TIMEOUT_MS` 的角色从"全局超时"降级为"应用级设置的缺省值"。

### D2 请求级超时的数据形态改为三态枚举，老值读时一次性升级

```
TimeoutSetting { Inherit, Unlimited, Custom(u64) }   // 缺省 Inherit
```

- 备选：沿用 `Option<u64>`，用 `u64::MAX` 表示不限制。被否——哨兵值会混淆"没填"与"不要超时"。
- 备选：保留 `Option<u64>` 另加 `unlimited: bool`。被否——三种状态由两个字段表示，非法组合可达。
- **应用级与请求级的 0 是两件事，别混**：应用级没有"上一层可跟随"，因此 `0` 在那里承担「不限制」（Postman 同一写法）；请求级已经有「不限制」这个选项，`0` 只是**指向同一个状态**的第二种输入方式，落库仍是三态里的 `Unlimited`，不会产生 `Custom { ms: 0 }` 这种第四态。后端另有一道保险：`effective_timeout` 把 `Custom { ms: 0 }` 也解析成不设超时——老行里可能留着裸 `0`，而 0 毫秒必然失败正是这次要消掉的坑。
- 兼容：`serde(default)` 使加字段对老行透明；读库时把老字段 `timeout_ms: Some(n)` 规范化为 `Custom(n)`，`None` 规范化为 `Inherit`。这一步是必要的——否则老请求的 1.5 秒会在用户无感的情况下变成 30 秒。

### D3 代理模式拆出「未配置」，让「不使用代理」成为真正生效的一层

新增 `ProxyMode::Inherit`（不生效，顺位到更低层级），把 `ProxyMode::None` 的语义收敛为「不使用代理（直连）」并让它始终生效。

- 现状的后果：`resolve_proxy` 会跳过 `ProxyMode::None` 的层，请求级界面又恰好写出 `proxy = null`，于是"不使用"与"未配置"不可区分，用户无法让某个请求绕过全局代理；`decide()` 里 `ProxyMode::None => Direct` 那一支因此不可达。
- 备选：用 `Option<ProxyConfig>` 的 `Some/None` 区分（`None` = 继承、`Some(None 模式)` = 直连）。被否——`ProxyConfig::default()` 是 `None` 模式，任何一处默认构造都会意外变成"直连"，判定无法局部阅读，而它恰恰是要修的这处混淆。
- 代价：既有断言 `ineffective_layers_are_skipped` 需要按新语义改写；`decide` 里那一支从死代码变为可达，要补测试。

### D4 代理凭据在写入边界加密，对外形状里没有凭据

```
   内存中 ProxyConfig 始终持有明文（与 CookieRow 同一取向）
        ^                                |
        |                                v
   解密：发送路径                   加密：命令层三处写入
   （调用方已持有 key_provider）     全局 · 环境 · 请求
```

- 备选：读取时统一解密（`global_proxy` / `get_environment` 各自解密）。被否——会把 `key_provider` 扩散到所有读取路径（集合树渲染也读环境），爆炸半径大；而真正需要明文的只有发送路径，那里已经持有密钥。
- 备选：把凭据搬到独立的存储表（照 Cookie 的做法）。被否——为一个密码建表偏重，且 `ProxyConfig` 分布在三处，搬出去要改三处引用与全部读取点；Cookie 能分列是因为它本来就有自己的表。
- 落库形态：`password` 由明文改为密文（字段改名以表明语义）。老字段不保留并存——三层都没有可填凭据的入口，不存在用户填过的密码。
- 必备配套：加密与解密时都调用 `register_secret_value`，否则日志脱敏出口不认识这个明文；解密失败映射为"不可读取"这一状态而非空值，避免静默变成"未设置"。
- 请求级不再保留"凭据填变量引用"这条路：该能力从未在界面上暴露（请求级代理界面只有模式、地址、白名单三行），而加密已取代了它的动机。
- 写入侧的协议必须区分「不改写凭据」与「清除凭据」：回传不再含明文之后，这两件事在界面上长得一样（都没填东西），因此必须在协议层分开——前者以"未提交该字段"表达，后者以一个显式的空值表达，后端分别映射为"保留既有密文"与"删除密文"。备选：用"留空即清除"一条规则。被否——留空与"用户什么都没动"不可分辨，一次误提交就会静默删掉凭据。

### D5 取消按「发送会话」注册，脚本桥与主请求共用同一会话

`send_request` 的入参追加发送会话标识；后端在状态里维护该会话下的在飞令牌集合；取消命令按会话撤销全部令牌。

- 为什么不是单个"在飞槽位"：一次发送里脚本可以并发发出多个 `pm.sendRequest`（宿主的事件处理是游离的异步任务，不阻塞脚本），所以同一会话下可能有多个在飞请求。
- 为什么不是"取消全部在飞"：会把本次发送之外的请求卷进来，且无法判定结果归属；将来若放开并发发送会直接出错。
- 结果裁决：后端返回"撤销了几个"只作为诊断，前端不据此判定本次发送的结果。实际结果由 `send_request` 以可区分的取消错误结束来表达——否则会出现"界面说已取消、响应其实到了"的竞态。

### D6 取消路径的资源收尾用 RAII，不写逐条补偿

在飞令牌与响应正文的落盘路径都交给守卫对象，正常完成时 disarm，取消与错误路径在 drop 时自动撤销/删除。

- 现状的问题：落盘文件的清理挂在已登记响应上，而登记只发生在正文读完之后；读正文途中取消会让该文件无人认领，在会话内累积（超大响应尤其明显，而这恰是最可能被取消的一类请求）。
- 备选：在取消路径逐条 `remove_file`。被否——需要枚举所有可能的中间产物，且错误返回路径同样会漏。

### D7 前端脚本段需要自己的取消出口，`dispose` 不能当作等待手段

`executeOne` 的 Promise 用 `Promise.race` 加一条取消出口；取消后走与阶段结束相同的 dispose 收尾。

- 依据：`disposeContext` 自己的注释已经说明——被终止的沙箱，回调可能永不触发。而 `executeOne` 唯一的兑现点是沙箱回调，所以用 dispose 去"等"会让 `performSend` 永不返回、发送态卡死（界面看起来"发送中"却没有任何请求在跑）。
- 不新增桥协议：`BRIDGE_EVENTS` 是受安全审计断言的有限具名集合。脚本内挂起的 `pm.sendRequest` 经既有的错误出口回执一个取消原因，不新开事件。
- `context.on` 没有取消订阅，清理只能靠销毁上下文——这与阶段结束的收尾是同一条路径，取消复用即可。

### D8 发送态与 `busy` 拆开

新增独立的发送态（记录哪个标签、第几次尝试）。取消只在发送态为真时出现；`busy` 仍用于禁用其它写操作。

- 现状的问题：`busy` 同时代表发送、保存请求、保存实体脚本与改名。把取消挂在它上面，保存期间会出现一个不该存在的取消入口。
- 发送入口在 `busy` 为真时仍然禁用（并发发送明确排除），但"禁用发送"与"呈现取消"是两件事。

### D9 取消对响应区不写任何内容

准确表述是"不动响应区"，而不是"回退到上一次"。

- 原因：取消可能发生在后置脚本阶段，此时响应区里放的是**本次**已经到达的响应。若按"回退到上一次"实现，反而会把用户已经拿到的结果丢掉。
- 因此 `performSend` 的失败分支必须区分取消——它现在无条件清空响应区。
- 本次已产生的脚本输出照常写回（沿用既有的"脚本输出不依赖响应"取向），于是可能出现"上一次的响应 + 本次的脚本输出"并存，这是那条取向的自然结果，不是新状态。

### D10 界面归属与控件形态

- 设置模态新增「请求」与「代理」两节：请求类偏好一处、代理一处。这与 Postman 的组织一致（请求类偏好在 General 的 Request 组，代理是独立的 Proxy 设置页），因此代理不并进「请求」节。
- 请求级超时的控件沿用代理的"模式下拉 + 条件细节行"：`.settings-row` 的控件列固定宽度，容不下"下拉 + 数值"两个控件并排，因此把数值项放成条件出现的独立行——与代理"手工填写才出现地址行"是同一种切换，用户已经学过。
- 「请求」一节的数值项用「数值 + 单位同框」（`[ 30000 | ms ]`），而不是「名称里带单位 + 整宽输入框」：后者把同一件事写成两行，用户还要把单位心算进值里。0 表示不限制，提示各一句，不写 Postman 那样的多行说明。格式化阈值不设这一档——它表达的是"超过多大不再结构化"，0 会让每一份响应都失去结构化视图，因此它保持档位下拉（越界档位不可选也由它表达）。
- 格式化阈值大于体积上限时不可选——用控件的可选状态表达依赖，不写解释性文案（`语义落在操作上`）。
- 代理密码控件表达"已设置/改写/清除"三态，当前状态落在行式列表已有的只读状态位上；提示收进 placeholder。

## Risks / Trade-offs

- **取消信号与脚本自然结束的时序竞争** → 以"取消标记已置位"为唯一判据：置位后不再写入本次的响应与脚本报告；本次发送的结果一律由后端可区分的取消错误裁决，前端不抢答。
- **老请求的超时值被静默丢弃** → 读库时一次性升级（`Some(n)` → `Custom(n)`）；若不升级，用户无感地从 1.5 秒变成 30 秒，属于最难被发现的一类回归。
- **代理凭据改为密文后，开发期手工写入的老行读不出来** → 按"凭据不可读取"呈现，不阻止请求发出；明确不写迁移逻辑（三层都没有可填凭据的界面入口）。
- **落盘文件清理依赖守卫正确 disarm** → 用一条用例钉住：大响应读正文途中取消后，断言响应目录里没有残留文件。
- **`ProxyMode` 的语义拆分触及既有断言与预览路径** → 既有断言按新语义改写，`decide` 中"直连"那一支从死代码变为可达并补测试；预览路径只取代理地址、不需要密钥，不受影响。
- **取消按钮占据主按钮位置** → 位置与发送相同（用户已经学过这个位置是"这次发送的开关"），取消不需要二次确认；但不沿用主色配色——否决性动作不占主色。
- **`0` 的两套约定在同一列表里并存** → 本变更统一为"0 非法"，并顺手修掉响应面板那处按"阈值大于 0"判断、而后端永远不会给出 0 的死分支。
- **取消位于前端与后端两侧，容易出现只完成一半** → 两侧的收尾都做成同一形状（守卫对象），并各有一条"取消后断言资源已收尾"的用例。

## Migration Plan

- **无 schema 迁移**：`requests.settings` 与 `settings` 都是 JSON 文本列，新增字段由 `serde(default)` 兜住；代理凭据的字段改名也只影响 blob 内部。
- **读时升级**：请求级超时的老值规范化为 `Custom(n)`；代理凭据的老明文字段忽略并视为未设置。
- **回滚**：新旧字段都在 JSON blob 内，旧版本会忽略未知字段，因此可直接回滚。回滚后表现为：老请求超时回到"跟随缺省"（即 30 秒）、代理凭据读不出来（请求不带代理认证）。两者都是功能退化而非崩溃，可接受。
- **部署顺序无约束**：前端与后端同包发布，不涉及协议兼容窗口。

## Open Questions

- 「某请求最终是否经由代理」在界面上是否需要一处常驻提示（现状只在响应元数据里有 `via_proxy`，解析预览里另有一个代理地址）。不影响本次 spec 与任务拆分。
- 环境级代理的编辑落点（在主区环境编辑器里作为一行，还是与变量表格并列的另一个区域）。spec 只要求落在环境自身的编辑面，两种实现都满足。
