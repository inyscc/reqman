## Context

代码库当前是未经改动的 Tauri v2 模板：Rust 侧仅有 `greet` 命令，`Cargo.toml` 只有 tauri/serde，`capabilities/default.json` 为 `core:default` + `opener:default`，`tauri.conf.json` 的 `csp` 为 `null`。本仓库此前无任何已归档能力规格（动机见 proposal.md — Why）。

约束它的是三件事：目标形态是离线单机工具（无云服务可作为一致性兜底）；前端被要求不具备文件系统、shell 与任意网络能力；`rodemap` 后续要求 Postman Collection v2.1 的往返基本不丢结构。最后一条会反过来约束现在就要定下的数据模型——它必须能容纳初始值与当前值、参数的启用/禁用标记、条目顺序、可继承的认证与脚本位，即使这些字段在本变更里还没有完整的使用者。

三个能力互为前提：HTTP 引擎需要变量解析，变量解析需要作用域真值，存储的 schema 必须预知请求与响应的形状。因此它们共处一个变更、共用一份设计。

## Goals / Non-Goals

**Goals:**

- 一套版本化、可迁移、可备份恢复的本地存储，且敏感值不以明文落盘。
- 一个纯函数式的变量解析器：既能用于真实发送，也能在不发送的情况下产出诊断结果，供界面提示未解析变量。
- 一个覆盖方法、各类正文、三级代理、证书开关与基础认证的网络层，且响应体积受控。
- 一条经得起后续 UI 能力复用的前端数据流：乐观更新 + 后端确认为准。
- 把应用权限面收敛到具名命令白名单，使「前端无通用文件/网络能力」成为可检查的事实而非约定。

**Non-Goals:**

- 三栏布局与各编辑器标签页（Params/Headers/Body/Auth/…）。前端只保留驱动命令、以及「未解析变量提示」与「secret 值掩码」这两个规格明确要求的界面行为所需的最小界面。
- Postman 集合/环境的导入导出。
- `pm.*` 脚本沙箱与集合运行器。设计只为它预留接入点，不实现。
- Cookie Jar、mTLS、OAuth 1.0/2.0、Digest、NTLM、AWS SigV4、JWT、Hawk、HAR/OpenAPI/curl 导入导出、代码生成。
- 历史记录界面、Mock、CLI 运行器、WebSocket/SSE/gRPC、性能测试、插件系统。
- Linux/macOS 的打包产物与安装包。代码跨平台，交付只保证 Windows。
- 主题、多窗口、快捷键、国际化、自动更新。

## Decisions

### D1. 前端不直连存储与网络，只调用具名命令

前端不获得通用文件读写、命令执行或任意 HTTP 能力；`tauri-plugin-sql` 这类把 SQL 暴露给前端的方案被排除。所有持久化与网络行为经具名命令进入 Rust。

*其他选项*：`tauri-plugin-sql`（把 SQL 交给前端，直接违背「前端无存储权限」）；暴露 `read_file(path)` / `generic_http(url)`（roadmap 明确禁止，等于把沙箱边界让给前端自觉）。

### D2. Rust/SQLite 为真值，前端做乐观更新

前端为每次编辑立即更新视图，同时提交后端，以后端返回的规范实体为准；失败时回滚到该实体上一次已确认的快照。同一实体的变更按序提交，避免重排请求竞态。前端不为跨实体事务承担一致性责任。

*其他选项*：前端为真值、异步写回（编辑最顺，但崩溃或写失败即产生前后端分歧，且与 D1 摩擦更大）；不做乐观更新（最简单，但树与表格操作有可感往返延迟，后续 UI 会持续受此拖累）。

### D3. SQLite 经 `rusqlite`（bundled）访问，WAL + 单写者

使用 bundled SQLite 以免依赖系统库；启用 WAL；写操作经单写者串行化，读走独立连接。数据库访问是阻塞的，一律在异步运行时的阻塞线程池中执行，不阻塞命令调度。

*其他选项*：`sqlx`（异步、编译期校验更严，但要在 Tauri 命令层再套一层运行时桥接，收益与本变更规模不匹配）；`tauri-plugin-sql`（见 D1）。

### D4. 迁移用 `user_version` 加有序步骤，每步一个事务，迁移前留副本

`PRAGMA user_version` 记录 schema 版本，迁移步骤按序、幂等、每步包在事务中；开始迁移前把数据库文件复制一份留在同目录，成功后才清理。失败则保持原库可用并报出失败原因，不留半迁移状态。

*其他选项*：引入 `rusqlite_migration` crate（机制等价，多一个依赖，收益有限）；散落的 `ALTER TABLE` 判断（难以保证幂等与「不损坏原数据」）。

### D5. Secret 值用设备级密钥加密落库，密钥存操作系统凭据库

操作系统凭据库只保管一把设备级数据密钥；secret 变量值用该密钥以 AEAD 方式加密后存入 SQLite。凭据库不可用时（典型是 Linux 无 Secret Service 会话），应用进入降级态：拒绝持久化 secret 值并明确告知，绝不退化为明文写入。将来引入主密码时，主密码只需在此之上再包一层。

*其他选项*：把 secret 值整体放进凭据库（隔离最佳，但批量读写变量时反复访问凭据库，条目多时受配额与性能限制）；P0 只做掩码、加密推迟（会直接违背规格中「不以明文落盘」）。

### D6. 日志脱敏收敛到单一出口

所有日志经过一个出口，在那里按头名黑名单（授权、Cookie、Set-Cookie、API Key 一类）与 secret 变量集合做字段级脱敏，并对已知 secret 明文值做一次值级清洗作为兜底。请求与响应正文默认不写入日志。

*其他选项*：在各调用点各自决定脱敏内容（漏一处即泄漏，且无法用测试整体覆盖）。

### D7. 变量解析是一个纯函数，产出值加诊断

解析器输入为有序作用域快照与待替换文本，输出替换结果与未解析占位符清单；真实发送与界面预览调用同一实现。参与解析的是「当前值」；「初始值」作为往返保真字段保留，不参与解析。

*其他选项*：发送时顺手替换，界面另行近似判断（会出现界面显示与实际请求不一致，直接违背规格中「发送前即可观察到」）。

### D8. 动态变量在发送时求值，且每次出现独立求值

`{{$guid}}` 一类在解析时刻生成；同一次请求中多次出现同一动态变量得到彼此独立的值。动态变量使用独立命名空间，用户作用域中的同名条目不会静默遮蔽它。

*其他选项*：持久化时即固化动态值（会让每次发送结果相同，违背该类变量的用途）。

### D9. 发送请求接受「已保存请求 id」或「内联请求载荷」两种入口

已保存请求按 id 执行，从存储读取；未保存的编辑态以完整载荷内联执行，不落库。两条入口共用同一执行路径，差别只在请求来源。

*其他选项*：只接受内联（未保存请求体验好，但每次执行都要前端拼全量载荷，容易漏字段）；只接受 id（迫使未保存请求先落库，会产生大量垃圾条目）。

### D10. 文件上传经一次性句柄，前端不能指定任意路径

文件选择由用户发起的对话框完成，后端登记所选路径并返回一次性句柄；发送请求只接受句柄，不接受路径字符串。这样前端即使被注入，也无法让后端去读取一个它自己选定的文件。

*其他选项*：把路径字符串从前端传回后端（等于给了前端一个「让后端读任意文件」的间接接口，与 D1 的意图相悖）。

### D11. TLS 用 rustls + 系统根证书，默认校验证书

选择跨平台一致的 TLS 实现，并读取操作系统信任库，使企业根证书可用，同时避免在 Linux 侧引入 OpenSSL 依赖。证书校验默认开启；按请求关闭时该请求在界面上带持续警示。

*其他选项*：`native-tls`（Windows 上走 schannel 对企业环境更友好，但三平台行为差异与依赖面更大）；rustls 内置 webpki 根（会漏掉企业自建根，离线内网场景常见）。

### D12. 代理三级优先在一处求解，`no_proxy` 在挂载代理前生效

请求 > 环境 > 全局的优先级在一个函数内求解，产出唯一生效配置；支持 HTTP/HTTPS/SOCKS5 与代理认证；目标命中白名单时不挂代理。系统代理在请求时刻读取，而非启动时固化。

*其他选项*：在发送处按层级依次覆盖（优先级语义分散，白名单与系统代理容易漏处理）。

### D13. 响应体积上限与分段取回

正文设置硬上限，超出即截断但保留状态码、耗时与体积元数据；超过格式化阈值时只提供原始视图，不做结构化解析。超大正文按区间取回，界面不一次性接收完整载荷；用户需要全文时由后端流式保存到用户选定的位置。

*其他选项*：全量载入内存再判断（正是规格要避免的内存失控）；超限直接报错（用户会丢失对本可保存内容的访问）。

### D14. 错误用单一可序列化枚举表达，带稳定分类

超时、域名解析失败、连接被拒、证书错误、代理错误、以及「收到响应但状态码非成功」被区分开，且错误中不含凭据明文。分类稳定，使规格中「失败类别可区分」可被测试断言。

*其他选项*：统一返回字符串（无法测试，也无从在界面上做差异化引导）。

### D15. 不可信响应的渲染隔离，同时预留给脚本沙箱

HTML、SVG、Markdown 预览在一个禁用脚本的独立上下文中渲染，该上下文不持有任何后端能力。后续 `pm.*` 脚本沙箱复用同一隔离机制，使 P2 替换为更严格的沙箱时是替换实现而非重写边界。

*其他选项*：直接在主文档里渲染（会执行响应携带的脚本，直接违背规格）；现在就上重量级沙箱（本变更范围外，属于过度设计）。

### D16. 先落地的数值默认

响应硬上限与格式化阈值先取一组保守默认值并作为常量集中定义，便于后续按实测调整。

### D17. 密钥来源可注入，测试用内存密钥

持有设备级密钥的提供者是一个可替换接口：生产实现访问操作系统凭据库，测试实现使用一次性的内存密钥。这样在没有凭据库的 Linux 环境与 CI 上，加密落库、解密与脱敏都能被完整验证，同时不引入任何面向用户的开发开关，也不存在明文回退路径。

*其他选项*：为 Linux 提供用户可见的「内存密钥」调试开关（把测试便利泄漏成产品功能，且存在被误用于真实数据的风险）；不做注入（加密相关验证只能在有图形会话的机器上手工进行，等于没有回归保护）。

### D18. 本变更的命令面清单

D1 声明的白名单在这里落成具体清单。命令名以本表为准；参数形态在实现时确定，但不得为本表之外的能力开口子。本变更不实现的 roadmap 白名单项一并标出，避免后续误以为已经存在。

| 分组 | 命令 | 对应规格 |
|---|---|---|
| 工作区 | `workspace_list`、`workspace_create`、`workspace_rename`、`workspace_delete`、`workspace_set_active` | storage-foundation |
| 集合与文件夹 | `collection_create`、`collection_rename`、`collection_delete`、`collection_move`、`collection_reorder`、`folder_create`、`folder_rename`、`folder_delete`、`folder_move` | storage-foundation |
| 请求 | `request_get`、`request_create`、`request_save`、`request_duplicate`、`request_delete`、`request_move` | storage-foundation |
| 环境与变量 | `environment_list`、`environment_create`、`environment_rename`、`environment_delete`、`environment_set_active`、`variable_list`、`variable_set`、`variable_delete`、`secret_reveal` | storage-foundation、variable-engine |
| 全局变量与应用设置 | `globals_list`、`globals_set`、`settings_get`、`settings_set` | storage-foundation |
| 变量解析预览 | `variables_preview` | variable-engine |
| 数据维护 | `backup_export`、`backup_restore` | storage-foundation |
| 网络执行 | `send_request`、`response_body_span`、`response_save_full`、`pick_upload_file` | http-engine |

本变更**不**提供 `import_postman_collection` 与 `load_history`（roadmap 白名单中的后续变更项）。roadmap 白名单里的 `save_environment` 由上面的环境与变量命令覆盖；`pick_upload_file` 在本变更以一次性句柄语义实现（D10）。

实现时发现上表只列了「写入」类入口，缺少界面渲染必需的**只读查询**，因此补入以下读命令（它们只做聚合与读取，不引入任何新的能力边界）：

| 分组 | 命令 | 说明 |
|---|---|---|
| 树读取 | `workspace_tree`、`collection_tree` | 聚合集合/文件夹/请求层级与顺序，避免前端拼装 |
| 当前状态 | `workspace_active`、`environment_active` | 活动工作区与活动环境 |
| 列表读取 | `environment_list`、`variable_list`、`globals_list` | 环境与变量列表（secret 取值在此已掩码） |
| 设置读取 | `settings_get`、`global_proxy_get` | 应用级设置与全局代理 |

**另加两条**落在安全边界上的补充，超出最初的设想但必要：`secret_reveal`（取得 secret 明文的唯一入口，与列表命令刻意分开以便审计）已在上面表中；`backup_export` / `backup_restore` / `response_save_full` / `pick_upload_file` **不接受路径参数**，路径由后端拉起系统对话框取得并留在后端。

本表是 tasks 1.3 收敛权限白名单与 7.2 安全边界审计的核对依据；`security_audit` 测试会逐条核对实际注册的命令面与本表一致。

## Risks / Trade-offs

- [交付目标是 Windows，而开发与验证环境是 Linux] → 代码保持跨平台，凭据存储与 TLS 走各自平台后端；把「Windows 上构建与冒烟」列为独立任务，不把它当作可以顺手完成的事。
- [设备级密钥随凭据库或用户配置迁移而丢失，导致 secret 值不可解密] → 只存"是否可解密"的标记，解密失败时报「不可读」而非静默清空；备份恢复时明确提示 secret 可能需要在目标设备重新录入。
- [SQLite 单写者在频繁乐观编辑下成为瓶颈] → WAL、按实体串行化的写入队列、合并同一实体的连续写入。
- [乐观更新失败时用户可能已经继续输入，回滚会吞掉输入] → 保留每实体上一次已确认快照，失败时显式提示并让用户选择保留本地改动或回退。
- [rustls + 系统根仍可能漏掉个别企业中间人根] → 保留按请求关闭校验的能力，但警示显著且错误信息保留原始证书错误，不做美化。
- [截断大响应可能隐藏用户真正需要的内容] → 保留完整元数据、明示已截断，并提供经后端流式保存全文的通道。
- [日志是凭据泄漏最可能的出口] → 正文默认不记日志；脱敏收敛到单一出口并为它单独写测试。
- [保留「初始值」而离线场景只有一个真值，容易让用户困惑] → 界面必须明确只有当前值参与解析，初始值定位为模板与往返字段。
- [单个变更覆盖三个能力，评审面偏大] → 以三个规格为契约边界，按 tasks.md 的依赖顺序分批落地与验证。

## Migration Plan

- 版本状态：本变更前无任何已发布版本、无用户数据，初始 schema 直接作为版本 1 落库；迁移执行器从第一天就在，但它的第一次真实使用发生在将来的变更里。
- 迁移步骤：读取当前版本 → 若低于目标，复制数据库文件到同目录备份 → 在事务中按序执行各步 → 成功后更新版本并清理备份；任一步失败则回滚事务、保留备份、报出原因。
- 回滚策略：首个正式版本发布前，回滚等价于删除本地数据库文件重新初始化；首个版本发布后，回滚需依赖迁移前的备份副本。
- 备份恢复：用户发起，导出为可恢复副本；恢复后用重新打开工作区的方式验证；secret 值是否可解密按设备密钥存在性判断。
- 无功能开关需求：本变更不改变任何已发布行为。
