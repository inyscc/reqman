## Context

动机见 proposal.md — Why。影响设计的是下面几处已核对的现状（`openspec/config.yaml` 里没有为任何 artifact 配置规则，因此只受这些事实约束）：

1. **`Dropdown` 已经有一套完整的定位实现**（`src/components/Dropdown.tsx`）：`useLayoutEffect` 里测量触发器与菜单的 `getBoundingClientRect` / `offsetWidth` / `offsetHeight`，垂直方向「下方放不下且上方更宽裕时翻到上方」，水平方向「先按 `align` 试一侧、放不下就收回视口内」，并把菜单 portal 到 `document.body` 配 `position: fixed`。`.dropdown-menu` 的注释写明了理由：「留在祖先里就会被 overflow 裁掉」。
2. **行内菜单没有走这套**：`NodeMenu.tsx` 只渲染内容，位置由 `.node-menu { position: absolute; top: 100%; right: var(--space-1); z-index: 20 }` 决定。它的两个宿主都是滚动容器——`.tree-root { overflow: auto }`（集合树）与 Environments 列表的滚动容器——被裁的路径完全一致。
3. **`useMenuDismiss` 的判定不依赖 DOM 子树位置**：它用 `ref.current.contains(target)` 判「点在菜单自身里」、用 `exemptSelector`（`.node-more`）豁免触发按钮、用「菜单之外的容器滚动」触发关闭。菜单 portal 到 body 之后，这三条判定照旧成立。
4. **标签宽度被 `min-width: 96px` 抹平**（`src/App.css`）：`.session-tab` 是 `flex: 0 1 auto`，内部 `{种类标记} {名称} {关闭格}` 没有任何元素吸收剩余宽度，于是内容不足 96px 时多出的宽度全落在右侧。请求标签因为方法徽标较长，通常已经超过 96px，所以看起来只有集合 / 文件夹标签有这问题。
5. **标签内三者的盒高不同**：种类图标是 12×12 的 svg（`icons.tsx` 的 `BOX`），方法徽标是 11px 文本（`--text-xs`），名称是 12px 文本（`--text-sm`），而 `.session-bar` 继承的行高是 1.5——三者的行盒分别是 12px、16.5px、18px，`align-items: center` 居中的是盒子而非字形。
6. **树里已经有一份「当前点击的实体」**：点击请求行走 `selectRequest` → `openRequest(id)`，点击目录行走 `onToggle` + `selectEntity` → `openEntity(...)`——**点击即打开**。树的高亮行也直接取自激活标签（`selectedRequestId={activeRequestTab?.requestId ?? null}`）。因此"当前点击的"与"当前打开的"是同一份状态，不需要新造一套。行内的 `activeId` 是**悬停态**（`useRowReveal` 在指针进入时设置、离开时清空），不能当作用对象。
7. **快捷键已有一处集中实现**：`App.tsx` 里一个 window 级的 keydown 监听（`Ctrl/Cmd + S`、`W`、`Tab`、`1..9`），刻意不依赖焦点位置，并在需要时 `preventDefault()` 吞掉运行环境的默认行为（如「保存网页」）。新增按键加在这一处即可。
8. **复制请求已有完整一条路径**：前端 `duplicateRequestById` → `client.requestDuplicate(id, null)`，后端 `duplicate_request` 从数据库读源请求（`..source` 整体复制，含脚本与认证）、生成新 id、名字缺省 `{name} 副本`；前端随后刷新树并打开副本标签。命令清单里**没有**文件夹或集合的复制。
9. **未保存改动的判定与模态壳都是现成的**：`isTabDirty(tab)`、`folderHasDirtyTab(tabs, subtree)`（后者已用于删除目录前的确认，接受一个子树 id 集合）；`Modal` 是既有的模态外壳，而 `modal` 是"同一时间至多一个"的单例状态。

## Goals / Non-Goals

**Goals:**

- 行内操作菜单与下拉菜单共用同一套「按可用空间决定方向、且不被容器裁剪」的定位。
- 标签宽度由内容决定，关闭入口贴在末尾；三类标签走同一套规则。
- 标签内的标记与名称呈现为视觉齐平。
- 树上的复制与重命名获得键盘入口，且与菜单入口同义。
- 目录可以整棵复制，落在同一个父级下。
- 复制不再静默丢弃未保存的改动。

**Non-Goals:**

- 不改标签的视觉权重（`.session-tab.active { font-weight: 500 }` 与 spec 中「非激活与激活标签 SHALL 等宽」的既存冲突另行处理）。
- 不改菜单的关闭规则、内部滚动行为、宽度规则与水平收边规则。
- 不统一图标系统。
- 不做集合级复制（会连带集合变量表，见 D8）。
- 不做菜单的键盘导航（方向键移动、回车触发）。
- 不让快捷键去读树的悬停态或菜单的展开态（见 D6）。

## Decisions

### D1. 把定位抽出来共用，而不是给行内菜单再写一份

依据：`Dropdown.tsx` 里那段 `place()` 已经是「垂直翻转 + 水平收边 + 测量后定位」的完整实现，行内菜单需要的正是同一套。

- **备选：在 `NodeMenu` 内复制一份。** 否决。理由与 `useMenuDismiss` 抽出来时写在同一文件头的那句话完全同构——两处的定位语义是同一套，复制一份等于承诺它们会一起漂移。
- **落点**：`src/lib/` 下一个 hook（例如 `useMenuPlacement`），输入触发器 ref、菜单 ref、对齐方式，输出菜单的 inline 定位与「是否需要 portal」。`Dropdown` 改用它，展开位置与行为保持不变。
- **保留差异**：行内菜单贴触发按钮的**右缘**（现状 `right: var(--space-1)`），下拉默认贴左缘、可用 `align="right"` 覆盖——抽出的实现要能表达这两种对齐。

### D2. 覆盖层的 z 序统一

`.node-menu` 现在是 `z-index: 20`，`.dropdown-menu` 是 `40`。`.dropdown-menu` 的注释给了理由：**要高于模态遮罩（20）与变量浮层（30）**。行内菜单 portal 之后同样要满足这一点，因此统一到 40。

行内菜单的选项固定为 2–4 个，不需要 `max-height`；抽出的实现保留 Dropdown 的「选项过多时内部滚动」行为，不额外为它加限制。

### D3. 关闭规则一行都不动

`useMenuDismiss` 的三条判定（见 Context 第 3 点）在 portal 之后全部成立，因此不改它，也不改 `NodeMenu` 传给它的 `exemptSelector`。顺带一个好处：树一滚动菜单就关，`position: fixed` 的坐标不会出现「菜单留在原地」的漂移。

### D4. 标签宽度：去掉撑开用的最小宽度，把剩余宽度交给名称

```css
.session-tab { min-width: 0; }                        /* 不再用固定宽度抹平 */
.session-tab-name { flex: 1 1 auto; min-width: 16px; } /* 剩余宽度归名称 */
```

`max-width: 260px` 与名称的省略号截断保持原样。

- **备选：保留 `min-width: 96px`，只让名称吸收剩余宽度。** 否决：关闭入口会被推到标签末尾、`×` 后面不再有空白，但**标签本身仍是 96px**，标签之间的大片空隙原样保留——与「后面不能有太多空白」的诉求只解决了一半。
- **`min-width: 96px` 原本承担的另一件事**（注释里写的：标签多时防止内容被压到 × 溢出）改由名称的可收缩性承担：压缩只发生在名称上，关闭格是 `flex: none`，不会被挤出。

### D5. 收紧行盒 + 统一文本型成员的盒高，而不是给图标做视觉微调

契约落在「三者的垂直中心一致」上，而不是「盒高必须相同」——后者是实现手段，换一种写法（例如收紧行高）同样能满足。

```css
.session-tab { line-height: 1; }   /* 行盒不再由继承的 1.5 撑高 */
.session-tab .tab-kind-icon,
.session-tab .method-badge,
.session-tab .session-tab-close { height: 16px; display: inline-flex; align-items: center; }
```

- **备选：给 svg 加 `margin-top` 或在 Y 轴上挪 0.5px。** 否决：magic number，字体或字号一变就失效。
- **残余差异**：字体自己的字形在盒内的分布（中文偏下、数字偏上）无法用布局消除，这一层不再修——`align-items: center` 保证的是盒子中心重合，这是可解释、可回归的边界。

### D6. 快捷键的作用对象是「当前激活标签的实体」

依据 Context 第 6 点：点击树行就是打开它，所以"当前点击的对象"与"当前打开的实体"本是一份状态（激活标签）。直接读它即可，不新增状态。

- **备选一：以被右键的那一行（`menuId`）为准。** 否决：右键**不会**打开那一行，于是"我点击了谁"与"我右键了谁"会分叉，同一组快捷键在同一屏上可能指向两个不同对象；而且菜单的开合状态会渗进快捷键的语义——关掉菜单行为就变，这不可解释。
- **备选二：让树维护一份"最后点击的行"。** 否决：它与激活标签会并行存在并互相漂移（点击折叠箭头、拖拽、键盘 Enter 都会改变"最后交互的行"而未必改变激活实体），多一份真相只换来更细的歧义。
- **搜索态**：作用对象不受搜索结果影响。过滤只改变**可见性**，不改变"当前点击的是谁"——被过滤掉的对象仍可复制或重命名。
- **菜单打开时的行为**：快捷键照常作用于激活实体，不因菜单开着而改变（与 D3 的"关闭规则不动"一致）。唯一的例外是重命名——编辑态不显示行末的操作入口，已打开的菜单会因此失去锚点（它锚在「⋯」上，而 `useMenuPlacement` 在锚点消失时不会重算位置，菜单会留在原地继续可用），所以进入编辑态时**收起菜单**。
- **模态打开时不生效**：树不是模态里的编辑面，而此刻复制键会真的发起一次复制、重命名键会把编辑态送进遮罩之后。这与 D7 的"让位给可编辑区域"是同一类判断——**这个键该由谁收到**。实现只看一个状态：`modal` 是单例，所以不存在"两个遮罩并存"的中间态。
- **带 Shift 的组合不生效**：`Ctrl+Shift+D` 之类在运行环境里另有归属。

### D7. 快捷键只在焦点不落在可编辑区域时生效

`Ctrl+E` 在 macOS 上是文本框的「移到行尾」（Emacs 绑定，肌肉记忆很硬），`Ctrl+D` 在代码编辑器里常被当作删除行或重复行。若照抄「保存」那条"焦点在输入框里也生效"的规则，用户会在输入框里改不动光标。

- **判定**：`event.target` 落在 `input` / `textarea` / `[contenteditable]` 或代码编辑器容器内时不触发。
- **与「保存」的差异是刻意的**，写进 spec——否则后来者看到同文件里两条相反的规则会当成 bug 修掉。
- **仍然 `preventDefault()`**：即使不触发本应用的动作，也要吞掉运行环境的默认行为（浏览器书签、页内搜索），避免"按了一下跳出去"。
- **重命名的可达性**：就地改名的输入框只在**该行被渲染**时存在（`view.renamingId === id ? <input>`），所以折叠目录里或被搜索词过滤掉的请求按下重命名键会"设了状态却看不见输入框"。因此触发前 SHALL 先展开其祖先链，搜索态下再清空搜索词（顺序上先清搜索，再展开）。这一条也写进 spec，因为它是快捷键独有的约束——菜单路径不可能遇到（能点到菜单就说明那行可见）。

### D8. 目录复制落在后端一条命令里

- **必须单次事务**：递归复制要逐层新建目录与请求。若前端串联多次 create，中途失败会留下半棵孤儿目录，用户只能手工清理。放在一条后端命令里，失败即整体回滚。
- **命名与位置**：名字缺省 `{name} 副本`（`duplicate_request` 已是这么写的，两处保持一致比另立规则更重要）；位置与源**同一个父级**，并且**紧跟在源之后**。
- **位置为什么不能图省事**：`duplicate_request` 原本把副本放在同级末尾（`MAX(sort_order) + 1`），实测反馈是"看着像没复制成功"——所以这两处一起改成紧邻。注意同级里目录与请求**共享同一组 `sort_order`**（`collection_tree` 按它混排，同序号时目录在前），因此顺序要取**混合**序列、插入新条目后按下标整体写回（`children_in_order` / `write_children_order`）。只给新条目算一个 `sort_order` 的话，同级里出现同序号条目时它会落到错误的一侧。
- **复制内容**：目录自身的认证与脚本、子文件夹的层级与认证脚本、其下请求的全部内容。文件名/表单等正文形态随请求整体复制（沿用 `..source` 的整体复制方式）。
- **不做集合复制**：集合级复制会连带 `scope = collection` 的变量行——副本的变量是否独立、取值是否需要用密钥重新加密，是一组独立的决策，不塞进本次。
- **收尾**：请求副本沿用现状（打开副本标签），目录副本展开（新目录若藏在折叠的父级里，用户会以为什么都没发生）。

### D9. 未保存改动挡住复制，用模态呈现

- **判定收在单一入口**：`duplicateRequestById` 是菜单与快捷键的共同入口，判定放这里，两条路径不可能分叉（若各写一处，行为差异就是缺陷，而 spec 明确要求一致）。
- **判定范围**：请求复制用 `isTabDirty` 看该请求；目录复制用 `folderHasDirtyTab(tabs, subtree)` 看整棵子树——**复用删除目录已有的工具**，两处对"这棵子树有没有未保存改动"给出同一答案。目录自身的脚本改动同样计入（`folderHasDirtyTab` 已覆盖 `entityKind === 'folder'`）。
- **呈现用 `Modal`**：用户要求的是独立的弹窗，而 `modal` 是单例状态（"同一时间至多一个"）。因此扩展该枚举加一个 kind、再用一个 state 承载要显示的名字，而不是并列渲染第二个遮罩——两个 backdrop 叠加会破坏既有约定，也会让 Esc 该关哪一个变得不确定。
- **不提供"放弃改动并继续"**：请求是"禁止复制"，给一个绕过的按钮等于把禁止降级成提示。

## Risks / Trade-offs

- **R1：标签宽度变化会让依赖 96px 的既有断言失败** → 改完先跑 `npm run test:browser` 与 `npm run test`，把断言按新行为更新，并在提交说明里交代这处行为变化。
- **R2：菜单 portal 化后要维持既有的「菜单内按下不触发容器拖拽」**（spec: ui-polish 有专门 scenario，会话标签行与请求区都涉及） → 抽出的实现复用 Dropdown 已验证的层级与结构，不新造 DOM 约定。
- **R3：极窄标签的可点性** → 名称 `min-width: 16px` 时标签最小宽度约 64px（图标 12 + 间距 + 关闭格 16 + 内边距），实现后目测确认。
- **R4：行内菜单在滚动时关闭** → 与既有行为一致（`useMenuDismiss` 第三条），不引入新的关闭路径。
- **R5：宿主可能吞掉 `Ctrl+D` / `Ctrl+E`**（WebView2 对某些组合键有自己的处理） → 与 `Ctrl+W` 同类的开放问题，处置方式相同：若宿主吞掉，菜单入口与快捷键清单相应调整，不影响其余逻辑；实现后实机确认。
- **R6：重命名前"先使其可见"会改变树的可见集合** → 清空搜索词与展开祖先链都是为了"让用户看得见输入框"，但它们也改变了用户当前的浏览状态。取舍：可见性优先（看不见的编辑态是更坏的结果），并且在 design 与 spec 里写明这一步。
- **R7：递归复制大目录耗时** → 单次后端事务、前端 await，沿用既有的加载处理；本变更不做进度流式反馈。
- **R8：`ModalKind` 是 `BottomBar` 导出的联合类型** → 扩展它需要同步该文件的定义，类型检查会兜住遗漏。

## Open Questions

- 行内菜单是否需要 `max-height` 与内部滚动：当前选项固定 2–4 个，暂不加。抽出的实现保留 Dropdown 的行为即可，将来选项变多时不需要改结构。
