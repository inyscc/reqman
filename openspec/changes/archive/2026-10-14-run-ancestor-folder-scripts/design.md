# Design

## Context

动机见 `proposal.md - Why`。与设计相关的现状：

- 编排只有三个槽位：`src/App.tsx` 发送前把集合、**直接父级**、请求的脚本拼成一个数组；`folder` 由 `draft.folder_id ? await client.folderGet(draft.folder_id) : null` 取得。
- 层级标签是**按索引**取的固定三段：`src/lib/scriptRuntime.ts` 的 `SCRIPT_LEVEL_LABELS = ['集合','文件夹','请求']`，`labelScript` / `formatScriptError` 都靠它；那里还有一段注释专门说明"过滤空脚本时必须保留原始索引，否则会把请求层标成文件夹层"。
- 数据模型里 `Folder` 有 `parent_folder_id`（迁移里就有），因此整条祖先链可以从数据库逐级取到，**不需要新的存储能力**。
- 归属的副本有好几处：树的节点对象、`requestStore`、已打开标签的草稿。拖拽只更新后端与树的结构，不改这些副本里的 `folder_id`——本次实测的失败正是从这里来的。
- 既有约定：脚本对 `pm.request` 的改动不跨段可见（`runScriptPhase` 接受一份 `request` 快照，三个层级共用）——链变长之后这条不变。

## Goals / Non-Goals

**Goals:**

- 目录层从"一个槽位"变成"递归祖先链"，前置与后置对称。
- 编排所依据的归属是请求**当前的**归属，不因界面上某一处副本陈旧而取错。
- 报错能指认到链上的具体目录。

**Non-Goals:**

- 不改脚本沙箱、`pm.*` 能力边界、超时上限与 secret 在脚本输出中的掩码处理。
- 不改集合层与请求层在链中的位置。
- 不为此新增后端命令（因此不动 `security_audit` 的命令白名单）。
- 不把"树的副本不许陈旧"抬成 `ui-layout` 的产品条款（见 D3）。

## Decisions

### D1 目录链按请求当前的归属上溯，逐级复用既有的 `folder_get`

发送时先按请求 id 取它当前的归属，再按 `parent_folder_id` 逐级上溯直到没有父级，得到由外到内的目录链。上溯时带 **visited 集合与深度上限**：坏数据成环时不得把发送卡死，超出上限时按已取到的链执行并报告一次错误。

**替代方案（否）**：只修"拖拽后同步草稿里的 `folder_id`"，继续用 `draft.folder_id` 上溯。这依赖"每一个持有副本的地方都被通知到"，将来任何新增副本都会重犯同一个错；而首次打开的标签、重启后恢复的标签、`pm.sendRequest` 发起的请求本身就可能没有干净副本。

**替代方案（否）**：新增一条后端命令一次返回整条链。少几次 IPC，但要过 `lib.rs` 注册与 `security_audit` 白名单；目录深度是个位数，不值得为此扩命令面。

### D2 层级标签改为"逐段描述由调用方给出"

`runScriptPhase` 的 `scripts` 参数由 `(string | null)[]` 改为携带标签的形态（`{ label, code }[]`，或并列传入 labels）：调用方给出「集合」/「目录名 · 第 N 层」/「请求」。`SCRIPT_LEVEL_LABELS` 与"保留原始索引"那段技巧随之消失——标签不再由位置推导。

同名目录 SHALL 以链上位置区分（例如「目录 · 文件夹 2（第 2 层）」），否则两个同名目录的报错无法区分。

**替代方案（否）**：保持固定三段，把整条目录链压成一段执行。报错无法定位到具体目录，而且"某一段抛错后是否继续下一段"的既有语义会变含糊——链上每一层都应是独立的执行段，与集合层、请求层平级。

### D3 归属副本的同步：实现卫生，不立产品条款

`applyTreeMove` 更新被移动请求的 `folder_id`，`moveNode` 成功后让受影响请求的 store 副本跟上，使"界面呈现的归属"与后端一致。

不为此新增 `ui-layout` 条款的理由：用户可观察的行为只有"脚本按当前归属编排"，它已由 `pm-script-runtime` 的一条场景覆盖；把"副本不许陈旧"写成布局类要求，等于把一条实现约束抬成产品契约。正确的处理方式是让副本只有一个来源（D1 让发送路径不再依赖副本），D3 只是把不一致本身也消掉——它是卫生，不是契约。

### D4 前置与后置共用同一份链

链在发送前算一次，收到响应后**复用**，不在响应之后再取一次归属。

理由：请求在飞行途中归属可能被改（用户拖拽、或另一个窗口改了同一个工作区），若后置重新解析，用户会看到"前置跑的是目录 A、后置跑的是目录 B"——比不对称更糟的是不可复现。

### D5 未归属目录时不编排目录层

请求直接挂在集合下时，链为空，目录层不参与本次编排。这是既有行为的保持（今天 `draft.folder_id` 为 `null` 时就是这个表现），规格里写明，免得实现时把它当成异常。

## Risks / Trade-offs

- [祖先链让发送前多几次 IPC 取目录] → 深度是个位数，逐级 `folder_get` 可接受；脚本执行本身的成本不变（过去只是层级少，不是每层更便宜）。
- [同名目录导致报错无法定位] → 标签带链上位置（D2）。
- [坏数据成环让上溯死循环] → visited 集合 + 深度上限（D1），超出时按已取到的链执行并报告，不卡死发送。
- [请求在飞行途中被移动] → 后置复用前置的链（D4）。
- [既有测试大量依赖"三段"的标签与 `scripts` 数组形态] → `tests/script-phase.test.ts` 是本变更最大的机械改动面；先改测试的表述（把标签当作调用方给的数据），再改实现，避免用旧断言逼出新实现里的临时兼容层。
- [`2026-09-27-align-script-order-and-pm-objects` 留下的"祖先脚本不执行"结论会与实现相悖] → 归档本变更时一并更正那处记载，避免下一个读它的人再得出相反的结论。

## Migration Plan

无数据迁移：`parent_folder_id` 早已存在，链是从既有数据推出来的；不涉及存储格式变化。

有一条**认知迁移**要跟随本变更：把 "文件夹层脚本只作用于直接子请求" 这个结论从项目记载里撤掉。

本变更**推翻** `2026-09-27-align-script-order-and-pm-objects` 留下的那条结论——它当时把"祖先目录的脚本不执行"记成了"与 Postman 相符，不改"，那处记载在该变更归档后的
`openspec/changes/archive/2026-09-27-align-script-order-and-pm-objects/proposal.md` 的理由段。

归档目录按惯例只读，因此**不强改归档里的文件**。更正的做法是让主规格 `openspec/specs/pm-script-runtime/spec.md` 的
「脚本执行时机与顺序」在归档本变更后成为链式表述（集合 → 递归祖先目录（由外到内）→ 请求），而推翻这件事本身记在这里。
