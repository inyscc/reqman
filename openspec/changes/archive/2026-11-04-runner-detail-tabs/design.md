# Design

## D1 按「哪一侧」分页，不按「头 / 体」分页

四分页（请求体 / 请求头 / 响应体 / 响应头）能一次看一个东西、互不遮挡，看起来最"干净"，但它把一次往返切成了四块互不相关的东西。排查时的问句其实是两句：「发出去的到底是什么」和「回来的到底是什么」；头与体是同一次发送的两半，分开之后要先想"我要看的是哪一半"才能点。

三个页签（请求 / 响应 / 脚本）与问句一一对应，也与 Postman Runner 的 Request / Response / Console 同构——用户从那边过来不必重新学。

**页签里头与体的位置**：两页都是「头在上、体在下」，与读的人嘴里的顺序一致（「请求头、请求体」）。头是一份"这次到底带了什么"的清单：短、要逐行核，排在最前面；体长，可能是几万字，放在最后——它长就让它长，不会把别的东西推到折叠线以下。两页同序，来回切时不必重新找位置。

## D2 请求页看的是「实际发出的那一份」，因此执行结果要带快照

请求编辑器里显示的是**草稿**：`{{base_url}}` 还没解析、认证还没落成、前置脚本还没跑。运行器要回答的偏偏是"脚本到底加了什么"——`Nonce`、`Sign` 这类只在运行时才存在的头，草稿里根本没有。

如果让界面拿草稿自己"重演"一遍解析，它会与真正的发送路径分叉，早晚对不上。因此快照由流水线在出口处给出（`RequestExecutionOutcome.sent`），与 trace 用的是同一份来源：

- 目标 URL 优先用后端回带的 `request_url`（前置脚本可能改写过去向），其次解析结果，最后草稿原文；
- 请求头成功时用 `request_headers`（认证头、正文的 `Content-Type`、`Cookie` 只有后端知道），失败时退回解析快照——它至少是「脚本改完之后、认证之前」的那一份；
- 正文用 `request_body`（后端只回带 `raw`）；没有响应时退回待发草稿里的 `raw`。

这也意味着快照要**在所有出口**都存在：失败、取消、门禁拦截时没有响应，但"本来要发的是什么"同样要能看见。

## D3 正文形态不是 `raw` 时，说明形态而不是留白

表单与二进制的正文没有原文可回读（后端只记 `raw`）。留一片空白会被读成"这条请求没带正文"，与事实相反。因此 `sent` 里带 `bodyKind`，界面按形态给一句话：「正文是 form-data 表单，运行器只呈现 raw 形态的原文。」

**被否掉的方案**：在界面侧把表单字段拼成 `k=v` 的伪原文。它不是真正发出去的字节（编码、边界、转义都不一样），一份看着像真的、其实不是的正文，比一句诚实的说明更坏。

## D4 换一条就回到默认页

页签只在这一次查看里有效：点开另一条时回到「脚本」，不沿用上一条停留的那一面。上一面是上一条的语境，带着它换人等于替用户预设这一条也要看同一侧。逐条比对正文因此要多点一次——但这个场景比"逐条看为什么挂了"少，默认落点让给后者。开新的一轮运行（`run()`）时同样重置回「脚本」。

## D5 默认停在「脚本」

跑完一条，最常问的是"它为什么通过或失败"。断言与 console 输出直接回答这个问题，就放在默认页；请求与响应是进一步核对才去的两页。断言结果虽然名单行上也有一个数字，但那只是结论，不是原因。

## D6 console 与断言仍然同页

「脚本」页保留 `ScriptReport` 原样（断言在前、console 在后）。运行器明细里的这份 console 是**按请求归拢**的，与全局 Console 那条混排时间线不是同一件事：前者回答"这一条为什么挂了"，后者回答"这一轮按什么顺序发了什么"。两处不重复，只是各自的切法不同。

## D7 顺带修掉的出口缺陷

`finish` 里读解析快照（`sandboxRequest`）的那条路，在**变量解析就失败**时走不到：那个 `const` 此时尚未初始化，出口自己会抛 `ReferenceError`，把原始错误盖掉。

本次把"待发请求头"提前成一个可变量（`snapshotHeaders`），由解析完成后赋值；出口读它，不再直接读那个 `const`。既有用例没覆盖到这条路径（解析失败要前端伪造一个抛错的 `variablesPreview`），因此补了一条回归用例。
