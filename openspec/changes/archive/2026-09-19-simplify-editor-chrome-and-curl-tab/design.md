## Context

动机见 `proposal.md - Why`，行为契约见本变更的 spec 增量（`specs/ui-layout`、`specs/variable-engine`、`specs/pm-script-runtime`）。这里只记录塑造实现方式的现状与约束。

- 请求带（`RequestBand`）目前同时承载身份、请求级操作按钮（另存为 / 删除 / cURL 开关）与解析预览条；cURL 的状态（`useCurlSnapshot`）也挂在 `RequestBand` 上，而内层标签由 `RequestEditor` 渲染——两者是**兄弟组件**，状态并不相邻。
- 请求编辑器的内层标签存于会话标签对象（`RequestSessionTab.innerTab`），随标签存续、不跨重启持久化。
- `Ctrl+S` 已存在且不依赖焦点：`App.tsx` 在 window 层监听，走 `editingRegistry.top()` 保存"当前生效的编辑面"，非脏时不发写请求。
- 编辑面注册表同时驱动 `Ctrl+S` 与"未保存守卫"（关闭脏标签、删除脏对应实体、退出应用前的询问）。集合/文件夹标签与设置模态都注册在其中。
- 未解析变量由后端解析时原样保留（`src-tauri/src/variables/mod.rs`），前端现有唯一提示位是解析预览条；响应区另有一条 `response.unresolved` 提示，但只在 `response` 存在且停留在 Body 标签时渲染。
- 全应用目前**没有**右键菜单（无 `onContextMenu`），也**没有**任何自动保存。

## Goals / Non-Goals

**Goals:**

- 请求带只剩身份与地址栏，请求级操作各有唯一归属（复制/删除在树、cURL 在标签、保存在快捷键）。
- 未解析变量成为发送前的硬判据。
- 集合/文件夹脚本与设置改为一处输入即落库，正常情况下不再有"未保存"概念（落库失败时仍保留保护）。
- 脚本编辑器真正铺满可用空间。

**Non-Goals:**

- 不改后端命令与数据模型：复用 `request_duplicate`、`collection_set_script`、`folder_set_script`、`settings_set`。
- 不动只读变量浮层（`VariablesPeek`）与环境选择器。
- 不重构响应区（除删除因拦截而失去意义的未解析提示）。
- 不为集合/文件夹新增复制能力（后端无对应命令）。
- 不把请求编辑器（含 Scripts 标签）改成自动保存。

## Decisions

### D1 保存模型：请求用 `Ctrl+S`，集合/文件夹脚本与设置用自动保存

请求编辑器承载一个完整对象的编辑（方法、URL、参数、头、正文、认证、设置、脚本），用户对"何时算改完"有明确意图，且对象可能很大；把它改成自动保存会在每次键入触发一次整对象写库，也使"删掉保存按钮"失去与快捷键的等价关系。集合/文件夹脚本与设置面板则相反：它们内容小、变更意图明确（就是"我改了这段脚本/这个策略"），且原本的保存按钮已经是唯一交互。

替代方案：三处统一自动保存（被否：请求对象大、写放大明显，且会连带推翻 `Ctrl+S` 与未保存守卫的既有语义）；三处统一 `Ctrl+S`（被否：脚本面板与设置面板是低交互频率的面板，用户更可能"改完就走"）。

### D2 自动保存之后，"脏"的含义自然变成"有未落库的改动"

集合/文件夹标签继续留在编辑面注册表里，**不需要摘除，也不需要新增开关**：实体标签的脏判据是"当前脚本与基线不等"（`App.tsx` 的 `isTabDirty`），只要**基线在每次成功落库后前移**，"已自动保存"就等于"不脏"。于是：

- 落库成功 → 标签不脏：会话标签不显示未保存圆点、关闭标签与退出应用不询问、`Ctrl+S` 在该标签上是空操作；
- 落库失败 → 基线不前移、标签保持脏：关闭标签或退出应用时守卫照常询问，用户选"保存并继续"即重试落库。

判定：这比"把实体标签从注册表里摘掉"更安全。摘掉之后自动保存一旦失败，退出时就没人再拦，改动会**静默丢失**——而自动保存恰恰是"用户从没按过保存"的场景，更需要这道兜底。

替代方案：把实体标签与设置面从注册表摘掉（被否：失败时静默丢改动）；保留注册但 `isDirty()` 恒返回 false（被否：同样丢掉失败时的保护）。

### D3 自动保存的时机与失败呈现

编辑停止后短暂延迟（约 500ms）落库，只在内容相对已落库值确有变化时写；写进行中再键入则合并为一次后续写。失败**不清空输入**，在面板内以就地状态呈现（"保存中… / 已保存 / 保存失败：原因"），用户继续键入即重试。状态是就地提示，不是模态、不阻塞编辑。

每次落库成功后前移该编辑面的基线；成功与否因此直接决定它还算不算脏（见 D2）。

替代方案：失焦即保存（被否：用户跨面板操作时容易与其它提交路径交叉）；每次键入立即保存（被否：写放大且错误反馈抖动）。

### D4 右键菜单与「更多」菜单是同一份菜单，逻辑不容分叉

请求节点的右键入口与 `⋯` 控件 SHALL 打开**同一份菜单**：同一份 `MenuItem[]` 声明、同一个展开状态（`view.menuId`）、同一套关闭规则（点外部、Esc、滚动）。两者只是同一状态上的两个触发器，SHALL NOT 各自维护一套菜单项或一套开关逻辑——否则"复制"这类后续新增项必然出现两处不同步。右键需 `preventDefault` 以屏蔽运行环境自带的页面菜单。

右键入口只挂在请求节点上：集合/文件夹当前没有可复制的后端命令，先不引入一个只会报错的入口。

替代方案：右键自带一套菜单（被否：同一节点两套定义，任一改动都要同步两处）。

### D5 复制请求要改成按 id 的版本，不能直接复用现有 `duplicateRequest()`

面板头按钮删除后，"复制请求"的**唯一入口**是树菜单，但现有 `duplicateRequest()` 取的是当前激活标签的 `draft`（`if (!draft) return`），而树菜单作用的是被右键的那个节点——两者可以不是同一条请求。做法是把这条流程改成接受请求 id 的版本（后端命令不变，仍是 `requestDuplicate(id, null)`），并保留既有收尾：刷新树 → 为新副本打开并激活一个标签，原标签与其草稿不动。

对"复制当前请求"这条路径，行为与原先的另存为完全一致；对"复制另一条请求"，同样为副本打开并激活一个新标签——与在树里点击该请求的体验一致，不需要额外确认。

### D6 cURL 状态从 `RequestBand` 下沉到 `RequestEditor`

cURL 的标签按钮与命令正文都渲染在 `RequestEditor` 内，而 cURL 的生成回调（`onCurl`）与快照状态目前在 `RequestBand`。做法是把 `onCurl` 一路传到 `RequestEditor`，`useCurlSnapshot` 也随之下沉；`RequestBand` 不再持有 cURL 的任何状态，`CurlPanel` 去掉"请求带展开"的语义，成为标签正文。

替代方案：把 cURL 状态提升到 `App`（被否：只有 `RequestEditor` 一处消费者，提升后要穿过 `RequestBand` 传空 props，收益为零）。

### D7 cURL 每次进入即重新生成，编辑不做保留

每次切换到该标签都按当前请求重新生成命令，上一次的编辑不保留——与既有的"收起再展开即重新生成"开关语义一致。真实用法是"进去、按需改一下、点复制走人"：把编辑跨标签留存没有价值，反而会让"命令是否还对应当前请求"变得不确定。要留用改动后的文本，用户在离开前点「复制」。

「重新生成」按钮仍保留：它让用户在不离开标签的情况下丢弃自己的改动、重新对齐到当前请求。「复制」保留：命令通常很长，手动全选不必要。

另有一条必须覆盖的情形：请求**换了**也要重新生成。同一标签的内层标签不会因为从树里点了另一条请求而复位（`innerTab` 仍停在 `cURL`），若只以"标签切换"为触发生成的信号，切换请求后会展示上一条请求的命令。因此触发生成的依赖是**当前请求的身份**与**是否停在该标签**两者，而不是标签切换这一个动作。

替代方案：跨标签保留编辑（被否：与真实用法不符，且使命令与请求的对应关系不再明确）；去掉「重新生成」（被否：请求改了之后无法在不离开标签的情况下重新对齐）。

### D8 未解析变量在 `performSend` 最前面拦截

拦截点是 `performSend` 的入口，早于脚本门禁、早于任何网络调用，因此脚本门禁放行后的重发同样被拦。判据用**发送时刻的解析结果**（复用 `variablesPreview` 的同一份输入），而不是界面上那份防抖的预览状态——后者可能比用户最后一次键入滞后约 200ms，会漏拦。拦截时不发请求，直接把错误（含变量名）写进现有的 `app-error` 提示位。

连带：既然未解析的请求永远发不出去，`response.unresolved` 的提示失去存在意义，一并删除。

实现时注意别解析两次：`performSend` 现有的那次 `variablesPreview`（供脚本取解析后的 URL）应上提到拦截处，成为唯一的一次，其结果同时用于拦截与脚本。否则启用脚本的请求每次发送会多一次解析往返。

替代方案：用界面上的 `preview` 状态判断（被否：可能过期）；在地址栏输入时实时拦截（被否：拦截的语义是"阻止发出"，不是"阻止输入"）。

### D9 删除解析预览后 `preview` 状态与轮询的去留

只读变量浮层（`VariablesPeek`）仍需要 `used` 与 `unresolved`，因此防抖轮询与 `preview` 状态保留，只是少了预览条这个消费者。`previewError` 随之失去唯一呈现位：预览失败不再打断界面，浮层在拿不到数据时降级为空列表。这是有意接受的信息损失——预览是辅助展示，失败不应比请求本身更显眼。

替代方案：把 `previewError` 也接到 `app-error`（被否：预览随每次键入重算，失败会把请求带刷成一片红）；连只读浮层一起删（被否：超出本变更范围）。

### D10 脚本编辑器铺满：打通 flex 链，而不是给固定高度

现状 `flex: 1` 落不到实际高度上，是因为链路上有两层没有参与拉伸：`.pane-body`（`overflow: auto` 的块级）与 Scripts 分支外多包的一层 `.stack`。做法是让该分支的容器参与拉伸（`flex: 1` + `min-height: 0`）并让正文区在脚本页不自带滚动，由编辑器自身承载滚动。

替代方案：给编辑器一个固定的较大 `min-height`（被否：只是"更高一点"，不随窗口变化，窄窗口下仍会出现大块空白）。

### D11 实现顺序（耦合关系）

标签集的扩展（`Tab` 联合类型加 `cURL`）与 cURL 状态下沉要一起做，否则中间态编译不过。自动保存与"实体标签退出编辑面注册"要一起做，否则会出现"自动保存了但仍被守卫询问"的错位。

## Risks / Trade-offs

- [两种保存模型并存] 请求靠快捷键、实体与设置靠自动保存，用户可能困惑 → 在实体/设置面板保留就地状态提示；在 `未保存` 标记的提示里点明 `Ctrl+S`。
- [自动保存的写放大] 长脚本连续键入会产生多次写 → 防抖 + 仅在值变化时写。
- [发送前拦截是行为收紧] 此前能发出去的请求会变成错误 → 错误文案必须列出未解析变量名，让用户知道改哪里；这是本变更唯一的 **BREAKING** 行为。
- [右键菜单依赖 WebView2 行为] 宿主可能自行弹出原生菜单 → 对请求节点 `preventDefault`，并在真机（`tests-browser`）验证原生菜单不出现。
- [cURL 正文铺满后长命令不再内部滚动] 原浏览器用例断言高度上限 220px 且内部滚动 → 该用例随之重写为"正文区自身滚动，且不挤压响应区"。
- [预览失败静默] 见 D9 → 记录为已知取舍。
- [脚本编辑器铺满依赖父级高度链] 若某一层仍有 `overflow: auto`，编辑器会退回内容高度 → 浏览器用例需断言"编辑器高度接近可用高度"，而不是只断言"比之前高"。

## Migration Plan

无数据迁移：改动是前端呈现与交互，落库命令与写入内容与改动前一致（自动保存写入的值就是原先点保存会写入的值）。

顺序：先做 cURL 标签（含状态下沉）与标签集扩展 → 再做面板头与预览条移除、树右键菜单 → 再做自动保存与守卫退出 → 最后做脚本区铺满与说明文字删除。每步之后跑前端用例与构建。

回滚：整体 revert 即可，无持久化副作用；唯一需要留意的是"发送前拦截"一旦发布，用户若已习惯发送未解析请求会立刻遇到错误——回滚该条即可恢复。

## Open Questions

- 右键菜单是否扩展到集合/文件夹节点，取决于后续是否引入集合/文件夹复制命令；当前无此命令，不做。
- 请求编辑器最终是否也转为自动保存（与实体/设置一致），属后续一致性议题，不影响本变更的 spec 与任务拆分。
