## Context

运行器的执行循环（`runSequence`）已经支持两种提前结束：用户按停止（`shouldStop`）、当前这条被取消（`result.status === 'stopped'`）。这次要加的第三种是**这一条失败**——它不是"人不想跑了"，而是"这一轮已经给了答案"。

三个问题要先定下来：默认开不开、什么算"失败"、收手之后界面上剩下那些行算什么。

## Goals / Non-Goals

**Goals**

- 一个可勾选的开关，勾上即"失败就收手"，不勾与现状完全一致。
- 收手之后能一眼看出**为什么停在半路**：断在第几条、哪条请求、还差几条没跑。
- 不引入第二套判定口径：什么算失败仍然由 `statusOfOutcome` 说了算。

**Non-Goals**

- 不做"失败重试 N 次""失败后跳到某一条""只重跑失败的那些"——那些是另一层编排，不在这一轮的范围里。
- 不把选择持久化到设置里。它与间隔一样，属于"这一轮怎么跑"，不是长期偏好。
- 不改单条发送的行为：失败即停只在运行器里成立。

## Decisions

### D1 默认不勾：两种意图，谁也不替用户先选

勾上是"快速回归 / 依赖链别连着挂"，不勾是"跑完看全貌"。同一份名单，两种意图都正当，因此默认取**保持现有行为**（不勾），让开关是一个可发现但不多管闲事的选项，而不是一次静默的行为变更。

代价是想要它的人得先点一下；相比"没打算停却被停掉"，这个代价小得多。

### D2 什么算"失败"：`fail` 与 `error`，不含 `stopped`

- `fail`：有断言未通过，或后置脚本抛了未捕获错误。
- `error`：请求没发出去（DNS、超时、证书……）或门禁没获准。
- `stopped`：用户主动取消。它本身已经让这一轮结束，不该再被记成"因失败停下"。

判定放在 `runSequence` 里对 `RunStepResult.status` 做，而不是回头去看 `RequestExecutionOutcome`——运行器的状态口径只有一处（`statusOfOutcome`），这里不再造第二套。

### D3 收手的现场留在面板里，而不是只从"少跑了几条"反推

`runSequence` 只返回已跑过的前缀，界面能算出"还剩几条"，但算不出"是谁停的"——用户按停止同样是前缀变短。因此 `RunnerPanel` 在每轮开跑时清空 `halt`，跑完再看三个条件同时成立才记一笔：开关是勾上的、`stopRef` 没被置位（不是用户停的）、返回条数少于名单条数且最后一条是 `fail` / `error`。满足时记下 `{ 第几条, 名称, 状态, 剩余数 }`。

这样"停止"与"失败即停"在界面上的表达不会串味：前者只是当前那条变灰、后面不再开跑；后者额外给一条横幅说明。

### D4 没轮到的行写「未执行」，不留白

名单里已跑的行都有状态点与摘要，没跑的行如果什么都不显示，读起来像"还在排队"。横幅已经说了"其余 N 条未执行"，行内再写一次不是重复——横幅是这一轮的结论，行内是这一行的状态，两者各说各的。只在 `halt` 存在时才标，正常跑完（含用户中途停止）不出现这个词，避免把"停止"也描述成"未执行"。

### D5 勾选状态不持久化

与「请求间隔」一致：都属于这一轮的执行设置。窗口关掉、重新打开，回到默认（不勾 + 间隔 0）。存进设置面板会让它变成一个跨会话的长期偏好，而它其实每次都可能不同。

### D6 设置项统一成「勾选框 + 一句自述」，解释收进行末的 ⓘ

设置列里原来只有「请求间隔」一项，写法是"标签在上、控件撑满整行、下面一行灰字说明"。加进第二项时若照搬这套，勾选框会变成"标签在上、一个孤零零的方框在下"，既不自然也和第一项对不上。

改成一份设置清单该有的形状：**每项都是一个勾选框 + 一句说明它自己的话**，左对齐竖排。间隔不是例外——它写成「☐ 请求之间等待 [ 0 ] 毫秒」，数字框嵌在句子里，勾选框是这一项的总开关（不勾即不等待，填的数字也不生效，因此不勾时数字框置灰不可编辑）。这样两项在视觉上是同一个句型，而不是"一个输入框 + 一个复选框"。

说明文字不常驻行下。设置项本身已经说清了它是什么，再各压一段灰字，只会让人以为那一项还有别的规矩要读。真需要补一句的（"什么算失败"、"第一条立即发出"）挂在行末的 ⓘ 上，悬停才出——原生 `title` 够用，不必自绘浮层。点 ⓘ 不该顺手勾上外层那一项，所以要吃掉它的点击默认行为。

副作用：整块高度从约 250px 降到约 130px，右列留白变多。这与"设置只占它该占的高度"一致，不额外补内容填空。

## Risks / Trade-offs

- **误以为默认就会停**：横幅文案里写明"已按设置结束本轮"，把因果关系说清楚；开关就在设置列的间隔下面，位置可发现。
- **失败即停会让"本轮共 N 条"里的 N 与已执行数不相等**：横幅与名单的「未执行」共同解释这个差额，进度条也停在断点上（它按已完成算，不假装跑满）。
- **`error` 是否该停**：请求根本没发出去时，后面的请求未必也会失败（不同的主机、不同的依赖），但仍归入"断了就收手"——它比断言失败更接近"这一轮没法继续"。
