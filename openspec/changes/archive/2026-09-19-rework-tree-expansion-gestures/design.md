## Context

折叠态是 `WorkspaceTree` 组件内的视图态 `collapsed: Set<string>`（记录被折叠的集合 / 文件夹 id，未记录即展开，因此默认全展开）。行的展开判定为 `expanded = view.searching || !view.collapsed.has(id)`，子节点以 `{expanded && children}` 条件渲染——**折叠一个父节点已经隐藏其整棵子树**。这一点决定了删除递归折叠不会损失任何可见效果，是本设计的关键前提。

当前手势：行内左侧箭头按钮 → `actions.onToggle(id)` 单节点切换（`stopPropagation`，不参与选中）；行容器 `onClick` → 去抖 200ms 后 `actions.onSelectEntity`；行容器 `onDoubleClick` → 取消待提交的选中 + `actions.onToggleRecursive(id, childNodes)`。

「选中」不是树自己的态：`App` 从激活标签派生 `selectedEntity` / `selectedRequestId` 并传入树，`selectEntity` 直接就是 `openEntity`。因此「树的选中」≡「会话标签栏的激活项」，这条一致性由 `ui-layout`「会话标签栏」需求明确要求。本设计把它当作不可破坏的约束，而不是要修改的对象——这是选择"单击不再是选中"这条路线而非"改选中语义"的原因。

## Goals / Non-Goals

**Goals:**

- 单击目录行 = 切换展开，即时生效，无去抖。
- 删除双击递归手势（视觉空操作）及其配套的去抖机制。
- 集合 / 文件夹的脚本面板保留可达入口，且鼠标与键盘语义一致。
- 展开态、搜索态强制展开、折叠不跨重启保留等既有约束全部沿用。

**Non-Goals:**

- 不改「会话标签栏中被激活的标签与树中选中保持一致」这条需求（本设计通过"单击不再是选中"让它继续成立）。
- 不改请求行行为（单击 = 打开请求标签）。
- 不引入折叠状态的后端持久化。
- 不做键盘方向键（← / →）逐层导航——它是"VS Code 式"的自然延伸，但需要独立的 roving focus 与方向键模型，本次不做。
- 不做拖拽排序、不做树行右键菜单。

## Decisions

**D1. 单击目录行是纯视图动作，不产生选中。**

浏览一棵树要逐层展开；若每次展开都开一个标签，标签栏会被"路过"的目录塞满。而「选中 ≡ 激活标签」是既有约束，因此唯一出路是让"单击行"退出"选中"语义——它只切换可见性，不通知 `App`。

- 替代方案（否）：单击 = 展开 + 选中 + 开标签。Postman 正是这样，但它的主区没有"每个实体一个标签"；本应用有多会话标签，叠加后会累积标签。
- 替代方案（否）：保留"单击 = 选中"，只把递归手势换个入口。等于不采纳 VS Code 式，回到逐层点箭头，用户已否决。

**D2. 脚本面板入口放「⋯」菜单，不加行内第二个控件。**

`ui-layout` 已规定"节点在悬停或获得键盘焦点时呈现**一个**「更多」控件"。加第二个控件要改这条需求、增加侧栏 chrome，并引入新的行内排除逻辑；加一个菜单项零 chrome，且菜单里的「重命名」本来就打开同一个面板，两者天然成组。

- 替代方案（否）：行内再加一个「脚本」图标按钮——违反既有约定，侧栏窄，需要新图标。
- 替代方案（否）：双击目录行 = 打开脚本面板。看似最通用（双击 = 打开），但双击的第一击**已经切换了展开态**，第二击再"打开"会留下"展开 → 回折"的闪烁；要消除闪烁只能给展开加去抖，与 D3 的零延迟目标自相矛盾。

**D3. 删除 200ms 去抖，用 `event.detail === 2` 忽略第二击。**

去抖的存在理由是"区分单击与双击"；新模型里双击不再有独立含义，这个代价就失去了理由。既然单击本身就是切换，第二击只需不重复切换，这个判断不引入任何延迟，键鼠手感随之统一。

- 替代方案（否）：保留去抖、只缩短阈值——依然是延迟，且要区分的那个"双击"已不存在。

**D4. 递归折叠 / 展开整段删除，不保留任何等价手势。**

折叠父节点已经隐藏整棵子树（`{expanded && children}`），递归折叠的可见效果与单节点折叠完全相同，唯一差异是"记忆"——后代目录自身的展开态是否被一并复位。这个"把展开记忆归零"的需求由 D5 覆盖；"一次性铺开全部层级"的需求由 D1 的逐层单击覆盖（成本已很低）。

- 替代方案（否）：搬到 Alt + 点击箭头，或节点菜单项——为一个视觉上无额外效果的操作新增不可发现的修饰键手势或菜单项，不划算。
- 替代方案（否）：节点菜单提供「折叠全部子目录 / 展开全部子目录」——同样是给空操作加入口，且菜单会膨胀到 7 项。

**D5. 工具栏只提供「全部折叠」一个控件，不提供「全部展开」。**

「全部折叠」替代的正是被删掉的递归折叠里唯一有价值的部分（把展开记忆整体归零），且 VS Code Explorer 的标题栏同样只有 Collapse All 一个按钮。树默认全展开，恢复路径是逐层单击（D1 已让这件事变便宜），第二个按钮边际价值低。

- 替代方案（否）：同时提供「全部展开」——多一个常驻控件，其效果等于树的初始状态。
- 替代方案（否）：一个按钮按当前状态在"全部折叠 / 全部展开"间切换——同一控件两种语义，用户无法预判下一次点击。

**D6. 全部实现落在 `WorkspaceTree.tsx`，`App.tsx` 不改。**

`onSelectEntity` 仍由菜单调用，`selectedEntity` 仍由激活标签派生，所以要动的只是"哪个手势调用哪个 action"。随之删除 `TreeActions.onToggleRecursive`、`collectFolderIds`、`EntryRow` 的 `childNodes` 属性、`SELECT_DEBOUNCE_MS` 与相关定时器。

**D7. 键盘 Enter 与单击同义。**

单击不再"打开"之后，若 Enter 仍走旧语义（打开面板），同一行在鼠标与键盘下会有两种含义——这正是本次要消除的那类不一致。Enter 改为切换展开，打开面板统一走「⋯」菜单。

## Risks / Trade-offs

[Risk] 进入脚本面板从 1 次点击变为 2 次（悬停 → 「⋯」→「编辑脚本」）。 → 面板是标签，打开后常驻，属低频动作；且「重命名」一直是同样的两次点击路径，用户对该路径已有预期。键盘用户可借"行获得焦点后「更多」控件显现"用 Tab 到达。

[Risk] 既有需求「新文件夹…且该父级处于展开状态」当前并未真正实现——`App.newFolder` 只调用 `folderCreate` 后重载树，不清除 `collapsed`。本次把"单击 = 折叠"变成主交互后，"折叠父级 → 在该父级下新建子文件夹 → 新文件夹不可见"会从偶发变成常见。 → 在实现中一并补齐。这是既有需求的既有缺口，不新增需求。

[Risk] 删掉双击手势会让习惯了双击递归的用户短暂困惑。 → 变化方向是"手势更少"：单击逐层展开更便宜，而且折叠父节点本来就能一次收起整棵子树，没有任何能力被回退。

[Trade-off] 单击目录行不再留下任何选中痕迹（无高亮）。 → 展开本身就是反馈；树里唯一的高亮仍是"当前打开的面板 / 请求"对应的节点，与既有需求一致。刻意不做"仅高亮不打开"的第二种高亮，避免一棵树里出现两种选中样式。
