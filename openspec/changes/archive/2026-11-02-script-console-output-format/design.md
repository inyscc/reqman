## Context

console 输出的呈现分两段：运行时把沙箱送来的**结构化参数**文本化（`formatConsoleArg`），视图层用 `pre-wrap` 按原文排版（`.script-console li`）。上一版只改了后者，前者仍在做两件与"可读"相悖的事——字符串里的行尾符原样塞进去（`\r` 在 HTML 里不断行），对象一律取紧凑 JSON（整份响应体一行几百字符）。

## Goals / Non-Goals

**Goals**

- 一条日志里只要含有"换行的意思"（`\n`、`\r\n`、`\r`），界面上就真的断开。
- 结构化值在超出一行的可读范围时展开成多行，层级看得出来。
- 短小的值仍是一行——省地方，也便于一眼扫过连续几条输出。

**Non-Goals**

- 不做可折叠的树形查看器（Postman 那种展开/收起）：这次只解决"读得下去"，交互另算。
- 不解释字符串里的字面量 `\n`（两个字符）。那会误伤"打印含转义的 JSON 文本"这一正常用法（`{"path":"C:\\new"}`）。
- 不改 console 的数据形状（`ConsoleEntry`）与收集时机；改动全部在文本化与样式上。

## Decisions

### D1 行尾符在文本化时归一，呈现层只认 `\n`

`pre-wrap` 只把 `\n` 当换行；`\r` 是普通空白，`a\rb` 会显示成 `ab`（中间那点空白还看不出来）。归一放在 `formatConsoleArg` 的入口：`\r\n?` → `\n`，一处收口，视图层与测试都只需管一种行尾符。

### D2 展开与否按**紧凑形态的长度**判定，阈值 80 字符

固定"对象一律摊开"会把 `{a:1}` 变成四行，连续几条短日志反而更难扫；固定"一律紧凑"则回到这次要解决的问题。以紧凑形态 80 字符为界：一行读得完就一行，读不完就摊开。80 大约是等宽字体下一屏行宽的舒适上限。

摊开用 `JSON.stringify(value, null, 2)`：与用户自己写 `JSON.stringify(v, null, 2)` 的观感一致，不需要为"我们的格式"另立一套认知。

### D3 截断按缩进后的文本算，提示独占一行

展开会让文本变长，因此截断判断放在**选定形态之后**：先决定紧凑还是缩进，再按最终的文本截断，避免"按紧凑形态算没超、展开后却超了"的漏网。截断提示前加换行——粘在被切断的残行后面既是噪声，又容易被读成日志内容。

### D4 `tab-size: 2`

缩进 JSON 用空格，不受影响；但脚本里手写的 `\t` 与手工对齐的表格会用到制表符，默认 8 列跳得太远，与相邻行的缩进对不上。

## Risks / Trade-offs

- **同一个对象可能这次一行、下次多行** → 取决于内容长度，属预期行为；阈值只影响观感，不影响信息量。
- **80 字符这个值带主观性** → 它只决定"读起来舒不舒服"，不构成契约；规格里写"超出可读长度时展开"，不把数字写死。
- **字面量 `\n` 不解解释** → 有意为之：解解释会破坏打印 JSON 文本的常见用法。需要真正的换行时，脚本里写真实的换行（模板字符串或 `\n` 转义）即可。
- **happy-dom 不加载样式表** → `tab-size` 与视觉折行只能人工确认；单测覆盖的是"文本里确实有 `\n`"这一半。

## Migration Plan

纯呈现层改动：无数据迁移、无命令变更、无存档兼容问题。回滚只需恢复 `formatConsoleArg` 的原实现与那条 CSS。
