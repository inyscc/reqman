## Why

`rodemap` 的 MVP/P0 清单里明确要求「Postman 导入导出」，验收标准第一条就是「能导入 Postman v2.1 集合并正确显示请求、变量、脚本、认证」。当前三个地基能力（`storage-foundation`、`variable-engine`、`http-engine`）已交付，数据模型在建立时就有意为往返留了槽位——`pre_request_script` / `test_script` 已存在于 collection、folder、request 三层，`AuthConfig` 已覆盖五种认证，变量已按五作用域落盘。缺的只是 Postman 文档与内部模型之间的**映射层**。

没有导入，用户无法把既有 Postman 资产带进来，一个 Postman 类工具因此无法被采纳；没有导出，用户无法离开。这两件事必须在继续往上叠（脚本执行、集合运行器）之前补齐，否则后续能力会建立在一个用户进不来的产品上。现在补映射层的成本最低，因为靶子（内部模型）已经稳定。

## What Changes

- 新增 **Postman 集合导入**：支持 Collection v2.1 与 v2.0，把 `item` 递归映射为集合/文件夹/请求，`event` 映射为前后置脚本，`auth` 映射为认证配置，`variable` 映射为集合变量，`body` / `url` 映射为请求体与 URL+查询参数。
- 新增 **环境与全局变量导入**：识别 Postman Environment 与 Globals 文档，映射为环境变量与工作区级全局变量。
- 新增 **Postman 集合导出**：以 v2.1 格式导出集合，导出时 secret 变量默认写入占位符而非明文。
- 新增 **环境与全局变量导出**：以 Postman 文档格式导出。
- 新增 **curl 导出**：把单条请求序列化为可执行的 curl 命令。
- 新增 **导入报告**：导入不静默消化差异，明确报告因不支持而降级的认证类型、被跳过的条目、降级为「未选择文件」的字段、被丢弃的示例数量。
- 明确 **三层映射与文件字段处置**：集合、文件夹、请求三级的认证与脚本各自落到对应实体，不压平到请求层；源文档中以本地路径描述的文件字段不被读取，降级为「未选择文件」并记入报告。
- 明确 **变量单值到双值的映射**：源文档的单一值在导入时同时写入初始值与当前值，导出时以当前值写出。
- 修改 **存储模型**：为集合、文件夹、请求补上 `description` 字段（Postman item 携带描述，缺失会导致往返丢结构），并引入 schema 迁移 v2。

**不做**（有意排除，见 design.md）：P1 的 curl / HAR / OpenAPI 导入；代码生成（curl / Python / JS / C# / Java / Go / PHP）；示例 `response[]` 的持久化与查看界面；GraphQL 请求体。

## Capabilities

### New Capabilities

- `postman-interchange`: 定义 Postman 文档与内部模型之间的双向映射契约——集合 v2.1/v2.0 与环境/全局变量的导入、集合与环境/全局变量的导出、curl 导出、secret 的占位符策略，以及导入过程中不可无损映射时的可观察处置（报告而非静默丢弃）。

### Modified Capabilities

- `storage-foundation`: 新增「条目描述持久化」需求——集合、文件夹与请求的描述文本被持久化并随条目往返，schema 版本推进到 v2。

## Impact

- **代码**：Rust 侧新增一个映射模块（Postman 文档的解析与序列化）与对应命令，接入既有存储层；前端新增导入/导出入口，并展示导入报告。
- **数据**：schema 从 v1 迁移到 v2（新增描述列）。迁移走既有的 `user_version` 有序执行器，失败不留下半迁移状态。
- **依赖**：需要 JSON 解析/序列化（Rust 侧已有 `serde`），不引入新的网络或加密依赖。
- **安全边界**：导入的来源可能是文件句柄也可能是粘贴文本，两者都不扩大前端权限；导出沿用后端拉起系统保存对话框、路径从不来自前端的既有模式。
- **兼容性**：不触及任何已发布接口，无破坏性变更。既有 v1 数据在迁移后保持可用。
