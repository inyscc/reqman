## Context

本变更位于三个已交付的地基能力之上（见 `proposal.md` - Why）。设计时可依赖的既有事实：

- 内部模型已为往返预留槽位：`pre_request_script` / `test_script` 同时存在于 `Collection`、`Folder`、`SavedRequest`（`storage/model.rs`）；`AuthConfig` 覆盖 `none` / `inherit` / `basic` / `bearer` / `api_key`；`Variable` 以 `scope` + `owner_id` 表达 env/collection/global，并有 `initial` / `current` 双值与 `is_secret`。
- 存储层的 schema 迁移执行器已就绪：按 `user_version` 有序执行、每步一个事务、迁移前复制数据库为备份、失败不留半迁移状态。
- 安全边界已定型：路径从不来自前端；文件访问一律经后端命令，导出沿用「后端拉起系统保存对话框」的模式（`backup_export` 的形状）。
- 请求的落盘字段与网络层共用同一 `SavedRequest`，导入只需构造该结构，不需要为导入单独开一条发送路径。

真正需要设计的是**映射的取舍**：Postman 文档的表达能力大于内部模型，差异必须被显式处置而不是静默消化。

## Goals / Non-Goals

**Goals:**

- 把 Postman v2.1 / v2.0 集合与环境、全局变量文档无损或「差异可见」地映射进内部模型。
- 让「导出 → 重新导入」成为可回归的一致性断言。
- 保持前端权限集合不因导入导出而扩大。

**Non-Goals:**

- 不实现 P1 的 curl / HAR / OpenAPI 导入，也不实现代码生成。
- 不为示例（`item.response[]`）建持久化表与查看界面。
- 不引入脚本执行——脚本在本变更里是**惰性文本**，可被搬运与往返，但不运行。
- 不改变变量解析优先级、网络执行或认证的实际发送语义。

## Decisions

### D1：映射层独立成模块，文档解析与序列化是纯函数

导入/导出不进 `storage`、`net`、`variables`，而是新增一个映射模块：一侧是 Postman 文档的解析/序列化（纯数据结构转换，不碰数据库），另一侧是落地到既有存储命令。

- **为什么**：纯函数部分可以只靠内存数据做往返断言，测试不需要数据库、网络或系统对话框；存储交互部分复用既有命令，避免第二条写入路径。
- **替代方案**：把解析写在命令处理函数里（否——解析无法独立测试，且命令层会膨胀）；用第三方 Postman 解析 crate（否——文档结构简单，且需要精确控制降级与报告，外部 crate 的取舍不可控）。

### D2：导入来源同时支持粘贴文本与文件句柄

命令接受两种输入：一段文档文本，或一个由 `pick_upload_file` 产生的一次性句柄。

- **为什么**：粘贴是纯字符串参数，不触碰文件系统，边界零成本；更重要的是它**可测**——原生文件对话框按项目既有约定不做自动化，而粘贴入口能覆盖完整的导入链路。
- **替代方案**：只支持文件句柄（否——导入主路径变得无法端到端测试）；只支持粘贴（否——大文件用户体验差）。

### D3：单份文档的导入是原子事务

解析与写入全部完成后才提交；任一步失败则整体不落盘。

- **为什么**：半份集合比拒绝导入更难收拾，且违背「不留下部分结果」的直觉。存储层已有事务能力。
- **替代方案**：逐条导入、允许部分成功（否——失败后用户无法判断集合的完整边界）。

### D4：不支持的认证降级为「无认证」并记入报告

遇到 digest / oauth1 / oauth2 / ntlm / awsv4 / hawk / edgegrid 等内部不支持的类型，映射为 `none`（明确「不携带认证」），而不是 `inherit`。

- **为什么**：`inherit` 会让请求意外继承集合级认证——一个用户没写过、也难以从文档推知的凭据会被发出去，属于错误方向的安全后果；`none` 是「什么都不加」，不会引入用户没预期的凭据。降级事实经报告暴露。
- **替代方案**：降级为 `inherit`（否——可能意外携带上一级凭据）；把不支持类型也存下来等将来支持（否——需要给 `AuthConfig` 加不透明槽位，扩大模型面，收益要等到认证补齐那天）。

### D5：示例 `item.response[]` 本轮丢弃，但必须计数上报

- **为什么**：示例需要新表 + 查看界面，是独立的一块；P0 验收只要求「请求、变量、脚本、认证」正确。丢弃本身可接受，**静默**丢弃不可接受——这由「导入报告」需求兜住。
- **替代方案**：本轮建表持久化（否——与「保存为示例」耦合，会把一个映射变更变成存储 + UI 变更）。

### D6：描述字段以可空列加入 schema v2

为 `collections`、`folders`、`requests` 各加一个可空 `description` 列。

- **为什么**：Postman 的 item 普遍携带描述，不补就违反「尽量不丢结构」；可空列是最小改动，既有行天然合法。
- **替代方案**：不补、导入时丢弃描述（否——描述是用户可见内容，属于能低成本保真的部分）；把描述塞进一个通用 `extra` JSON 列（否——为将来未知字段开的口子会迅速变成垃圾桶，且查询与迁移都更难）。

### D7：源文档中被禁用的变量跳过并上报

Postman 允许单个变量处于禁用态；内部 `Variable` 没有启用位。

- **为什么**：给 `Variable` 加 `enabled` 列会波及变量解析、列表界面与全部既有测试，代价远大于收益；而「禁用变量不参与解析」与「跳过」在解析结果上等价，差别只在是否可见——用报告让差别可见即可。
- **替代方案**：加 `enabled` 列（否——扩大面）；导入为启用（否——静默改变语义，用户以为禁用的值参与了解析）。

### D8：secret 以固定占位符进出

导出时 secret 值写成占位符（而非明文）；导入时识别该占位符并把变量还原为 secret、值置空。

- **为什么**：这是 rodemap §4 P0「导出 Collection 时 secret 默认占位符」。让占位符可被自己识别，往返才不会把 secret 变成明文或垃圾值。
- **替代方案**：导出省略 secret 变量（否——往返后变量丢失，比占位符更差）。

### D9：curl 导出使用解析后的实际值

生成的命令使用变量解析后的真实取值（含认证凭据），与 Postman 的 "Copy as cURL" 行为一致；该值随命令返回界面，不写入日志。

- **为什么**：curl 导出的用途是「拿出去直接跑」，占位符会使其不可执行；它是用户对单条请求的一次显式动作，与「会被流转的导出文件」不同类。日志脱敏是既有单一出口，凭据照旧不进日志。
- **替代方案**：curl 中也用 secret 占位符（否——命令不可执行，失去该功能的主要价值）。**注意**：含 secret 时命令内容即明文，需求据此写成「当请求不引用 secret 变量时 SHALL 可直接执行」，把边界写清楚而不是假装没有。

  实现时又发现同类边界：**请求体引用本地文件时（多段表单的文件字段、二进制正文）命令天然不可直接执行**——文件路径按设计从不进入后端，只能写占位符。这是 D12 的同一取舍在 curl 上的投影，不是可以绕过的实现细节。因此需求的可执行条件写成「既不引用 secret 变量、其请求体也不引用本地文件」，并要求在不满足时仍产出结构完整的命令且显式告知原因；`CurlCommand.warnings` 是这条的落点。

### D10：重复导入总是创建新集合

导入不按 `_postman_id` 或名称做合并/覆盖。

- **为什么**：合并语义需要冲突解决策略，是一个完整特性而非导入的附庸；「总是新增」行为可预测、可撤销（用户可删）。目标工作区由用户在当前工作区上下文中决定。
- **替代方案**：按 `_postman_id` 幂等覆盖（否——需要定义冲突时保留谁，本轮不划算）。

### D11：集合级与文件夹级的认证、事件各自落到对应实体

内部模型的 `Collection` 与 `Folder` 本就带 `auth` 与前后置脚本槽位；Postman 的集合级、文件夹级 `auth` 与 `event` 直接映射到这两个实体，而不是压平到请求层。

- **为什么**：模型为继承预留了这些槽位；压平到请求层会同时丢结构（集合级配置被复制进每个请求，原层级信息消失）并改变继承语义。
- **替代方案**：只保留请求层（否——与「尽量不丢结构」冲突，且集合级认证会退化成逐请求复制）；只保留集合级、忽略文件夹级（否——文件夹级 auth/event 是 Postman 的常见用法）。

### D12：文件类字段降级为「未选择文件」并进报告

Postman 的 `formdata` 文件字段与 `binary` 正文以 `src` 本地路径描述文件。导入不读取该路径（安全边界：路径从不来自前端），而是保留字段名与描述、置为未选择文件。

- **为什么**：读取 `src` 会让一份文档内容决定后端去读哪个本地文件，正是既有句柄机制要防的事。保留字段让用户重新选择文件即可恢复，且差异经报告可见。
- **替代方案**：读取 `src` 指向的文件并登记为句柄（否——越过安全边界）；整类拒绝导入（否——一个文件字段不该让整份集合进不来）。

### D13：单一值同时写入初始值与当前值，导出取当前值

源格式的变量只有一个值，内部有初始值/当前值两列。导入把该值写入两列；导出以当前值写出。

- **为什么**：导入时两列一致最贴近直觉（刚导入的变量没有「被改过的当前值」）；导出取当前值，因为那才参与解析、也是用户当下看到的行为。Postman 格式无法表达两值差异，因此该差异在往返中不保真——需求已把保真范围限定为变量名、secret 标记与当前值。
- **替代方案**：导入只写当前值、初始值留空（否——界面上会出现无来由的空初始值）；导出取初始值（否——导出用户当下实际使用的值更符合直觉）。

## Risks / Trade-offs

- **[降级被用户忽略]** → 导入报告必须出现在导入动作的返回结果里并直接可见，而不是只写进日志。
- **[curl 导出泄露 secret 明文]** → 这是 D9 的自觉取舍；需求把「可直接执行」限定在不含 secret 的情形，界面在该情形下给出提示，且命令不进日志。
- **[curl 导出引用本地文件时不可直接执行]** → 同样是自觉取舍：内部只持有一次性句柄，路径不进后端。命令里写占位符并给出警告，避免用户拿到一条静默失败的命令。
- **[schema v2 后的降级（downgrade）不安全]** → 迁移是向前的：加列后旧版本应用会用未知的 `user_version` 继续运行并按列名读取，`description` 列的存在本身不破坏旧查询，但若将来出现不兼容变更，旧版本会读不懂。缓解：迁移执行器已有的备份机制 + 本变更只做可空加列这一最小步；README 的「已知限制」应记录「迁移向前，不支持回退到旧版本」。
- **[URL 结构双向映射的保真]** → Postman 的 `url` 是结构化对象（`host[]` / `path[]` / `query[]` / `variable[]`），内部是扁平字符串 + 参数表。往返断言以「重新导入后结构一致」为准，而不是「文本逐字节一致」；路径变量取值与 `:id` 的对齐是此处的易错点，需要专门用例。
- **[v2.0 与 v2.1 差异]** → 两者条目形状相近但有细节差别（如 URL 的字符串/对象形式）；解析器按「先探测版本、再归一化到同一中间表示」处理，避免两套映射逻辑分叉。
- **[示例丢弃量被低估]** → 报告中的示例计数是用户判断「这次导入丢了多少」的唯一依据，必须在嵌套条目上递归统计。
- **[集合与文件夹级配置被压平]** → 需求显式要求认证与脚本在三个层级各自落位；验收需覆盖「上层认证在其下未显式覆盖的请求上按继承生效」，否则压平会以「测试仍通过」的方式漏过。
- **[文件字段导入后不可直接发送]** → 这是 D12 的自觉取舍：用户需重新选择文件。报告列出受影响条目，避免用户在发送时才意外发现。
- **[初始值与当前值的差异不保真]** → Postman 格式只有单一值；导出取当前值，且需求已限定往返保真范围，不视为缺陷。

## Migration Plan

1. 迁移执行器追加 v2 步骤：为 `collections`、`folders`、`requests` 增加可空 `description` 列。既有 v1 数据库在启动时自动迁移，迁移前自动备份、失败则原数据保持可读。
2. 模型与存取层补上描述字段的读写；由于列可空，旧数据读出为 `None`，无需数据回填。
3. 导入导出命令与前端入口随后接入，不改变既有命令的签名语义。
4. 回滚策略：本变更只新增列与新增命令，不修改既有命令契约；代码回滚后旧数据仍可读（`description` 列被忽略）。向前迁移的数据库不建议回退到旧版本应用，这一点记入 README 的已知限制。
